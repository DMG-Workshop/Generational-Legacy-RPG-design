# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Godot 4.7 with GDScript. Commands assume `godot` is on the PATH.

- Import assets and scripts (once in a fresh checkout): `godot --headless --path . --import`
- Play the game: `godot --path .` (main scene `ui/main.tscn` loads `main.gd`, which starts `ui/play/game_app.gd`)
- Run one test suite: `godot --headless --path . -s res://tests/test_game_round.gd`
  - Exit code 0 means pass. A suite prints `N checks, M failures` (or `ALL PASS`) and exits 1 on any failure.
- Run every game suite, one after another:
  `for t in tests/test_game_*.gd tests/test_round_determinism.gd; do godot --headless --path . -s res://$t || echo "FAILED $t"; done`
- Never run suites in parallel on one machine. They share the `user://` save files and fail when they overlap.
- CI (`.github/workflows/tests.yml`) runs the same suites on every pull request, one job per suite. It also fails a suite that prints `SCRIPT ERROR` even when the exit code is 0. Look for that text when you run suites by hand.
- Debug Android APK: `godot --headless --path . --export-debug "Android" build/GenerationalLegacy-debug.apk` (the Android SDK and JDK are configured in Godot's editor settings). The iOS preset only exports on a Mac with Xcode.
- Desktop builds: `godot --headless --path . --export-release "Linux" build/linux/GenerationalLegacy.x86_64` and `--export-release "macOS" build/macos/GenerationalLegacy.zip` (and `"Windows Desktop"`), each needing its export template installed (`.github/actions/setup-godot/action.yml` lists them). The macOS zip is ad-hoc signed and builds on Linux. `.github/workflows/release.yml` builds all of them on a release and on any pull request that touches it, the setup action or `export_presets.cfg`; `docs/RELEASING.md` says how to run each.
- Check all the data at once: `godot --headless --path . -s res://tools/check_data.gd`. It parses every JSON file under `data/`, runs every system's `validate()`, and checks the text catalog; it prints the problems and exits 1 if there are any. `tests/test_game_data.gd` runs it, so CI does too. A new `validate()` goes into `tools/check_data.gd`.
- Replays: `godot --headless --path . -s res://tools/replay.gd -- record SEED CLASS RACE COMMANDS [FILE]` has the autopilot live a run and prints (or writes) its replay block; `-- play FILE` plays one and exits 1, saying where, if it no longer holds on this version of the game.
- Error reports: `godot --headless --path . -s res://tools/report.gd -- read FILE [OUT.glsave]` says what a player's report holds, checks its save loads, and with OUT writes that save as a house backup to load in the game; `-- make SEED COMMANDS [FILE]` makes one from an autopilot run. It exits 1, saying why, on a file that is not a readable report.
- Long run: `godot --headless --path . -s res://tools/long_run_check.gd -- [seeds=1-2] [gens=60] [races=human,elf] [check]` has the autopilot play whole dynasties for many generations and holds each to the budgets in `data/game/budgets.json` (save size, load time, time per generation, journal size, the line carrying on). `.github/workflows/long-runs.yml` runs it every night, one race per job, and can be started by hand. A change that makes saves, loading or generations much heavier shows up there; raise a budget only on purpose, in the same change.
- Screenshots: `xvfb-run -a -s "-screen 0 1280x720x24" godot --path . --rendering-driver opengl3 --audio-driver Dummy -s res://tools/screenshots.gd -- mode=check` draws the key screens with the real renderer on a virtual display and compares them with `tests/screenshots`; `mode=update` makes the stored images again. `.github/workflows/screenshots.yml` runs the check on every pull request and keeps what it drew as an artifact. A change that moves a screen or the art must update the stored images in the same change (tick "update" when starting the workflow by hand on the branch, or run `mode=update` locally); the diff of the PNGs is what the reviewer looks at. `mode=store` draws the store page's pictures instead (`STORE_SHOTS`: six screens at 1920x1080 and the phone layout at 2532x1170) into `build/store`; it needs a display at least that big (`-screen 0 2600x1200x24`) and compares nothing.
- Rendering trial (throwaway, roadmap item 36): `godot --path . res://trial/iso_trial.tscn` runs it on a computer; the "Rendering trial APK" workflow builds it as its own Android app, and `tools/trial_adb.sh` records battery and temperature while it runs on a phone. It is left out of the game's builds. `docs/RENDER_TRIAL.md` has the method, what counts as a pass and the results table; nothing has been measured on a phone yet.
- Balance harness: `godot --headless --path . -s res://tools/balance_harness.gd` (the autopilot plays 12 seeds x 8 races x 10 generations, in parallel processes, about 4 minutes on 4 processors). Battle deaths should stay in the 3-7% band. Run it on the commit before a balance change and on the change with the same arguments; `docs/BALANCE.md` explains how to read the figures, which are noisy per seed.

## Architecture

Only the text game is wired into the app. The older prototype code is described at the end of this section.

- **Logic and rendering are separate.** `core/game/` makes no UI calls. `ui/play/` screens read dynasty state and call its methods, and they never compute results. New rules go in `core/game/` with a test in `tests/`.
- **Content is data.** `GameData` (`core/game/game_data.gd`) loads every JSON file under `data/` once, through `load_all()`. The tunable settings are in `data/game/balance.json` (Hard hunt rules, death chance), `data/combat/rounds.json` (party rounds), `data/classes/classes.json` (class skills, auto-battle `style`, openers) and `data/ui/mobile.json` (touch and layout sizes). Don't hardcode numbers in code.
- **State lives in `GameDynasty`** (`core/game/game_dynasty.gd`): the heir, the party, the world, the current battle, `command_round` and `auto_party`. It saves through `to_dict()` and `from_dict()`. A new field must load from an old save, and needs a test for that.
- **Battles.** `GameBattle` owns the round: heir, allies, foes, events and log. Its `round_on` hold lets manual party rounds use the same methods, and it is inert when no party round is open. `GameTactics.auto_turn` picks actions for auto-battle, the autopilot and any party member on Auto. `GameRound` queues manual party commands, resolves them together and retargets members who have died. A member's standing cover (`GameRound.set_cover`) is passed to the foe phase as `GameBattle.round_covers`; `_cover_for` redirects one blow a round aimed at a member below `cover_below`, drawing no dice, so a fight with no cover set plays exactly as before. With `GameRound.ask_reactions` on (only the battle screen sets it; tests, the golden scenarios and the autopilots leave it off), a foe about to strike a member below `cover_below` stops the round: `GameBattle.reaction` holds the blow, the foe phase waits in `_foe_queue`/`_foe_step`, and `GameRound.answer` strikes it and plays on. Letting it land draws no extra dice, so it plays exactly as a round that never asked.
- **Battle events.** The typed events a fight puts in `GameBattle.events` (and `GameRound` adds its round, act and foes markers to) are listed with their fields in `data/game/battle_events.json`; `GameEventSpec.problems` checks one against it. A new event, or a new field on one, goes on the list in the same change: `tests/test_game_event_list.gd` fails on an unlisted type or field and on a source type missing from the list. Life actions return text lines and emit no typed events.
- **Autopilot.** `GameBot` (`step`, `live_life`, `wants_hard_hunt`) plays without input for the tests and the "Auto" buttons. Changing when it or the battle draws a random number changes every seeded fight, and the determinism tests will catch that. **Profile bots** (`GameProfile`, core, no UI; `docs/BALANCE.md`): layered on `GameBot.live_life` through three hooks that are off by default (`live_life`'s `hook`, `GameBot.flee_below`, `GameBot.on_fight_end`), so with no profile the autopilot is unchanged. `balance_harness.gd -- profile=<forge|miner|builder|farmer|breeder|forager|fleer|trialist>` reports the gold-equivalent gain (`GameProfile.net_worth`) and the player actions per life. A profile only ever calls the same core functions the screens call; its policies are first guesses.
- **Contact in the open world.** `GameSandbox._contact()` (after each creature tick) starts a fight when a creature in `chase` mode comes within `contact_range` of the heir on the ground floor of the open world (never upstairs or indoors): it and other hunters within `contact_join`, up to `contact_max` (all in `data/world/sandbox.json`), go to `GameDynasty.start_encounter(ids)`, which builds them with the hunt's own rules (`balance.json` `hunt_rewards.hunt`, levels round the heir's, `battle_kind` "hunt") and takes them out of the open world. It draws from the dynasty's dice, so only the sandbox calls it; the autopilot and golden scenarios never do. The screen already hands a battle to the battle screen. **Walls stop it:** a creature only reaches the heir if the straight line between them is clear (`GameSandbox.reaches_heir`, `GameWalls.line_clear`: a wall, tower, town building or shut gate stops it, a corner step between two solids stops it, a tree does not; sampled every `reach_step` tiles), so a creature pressed against the outside of a town wall starts no fight with a heir on the inside. Pure, no dice. The full rules are in `docs/REACH.md`. Melee contact is wired; the other channels are pure functions in `GameReach` (`core/game/game_reach.gd`, `reach` in `data/world/walls.json`: each stopper kind lists the channels it stops, walk, melee, ranged, area, sight, so bars and slits stop a blow but not a shot or a look): `line_clear` by channel, `shot_ok` (range, arc lob), `area_hits` and `aimable` (shadows), `sees`, `keeps`, `loses_interest` (`chase_detour_mult` in `behaviour.json`), `flank_point`, `knock`, `pull`, `blink_ok`. They are not yet called by the creature step, companions or battle (that would change seeded play), and the map has no bars or slit tile yet. `tests/test_game_reach_rules.gd` checks. `tests/test_game_sandbox_contact.gd` and `tests/test_game_reach.gd` check.
- **The heir upstairs.** `GameSandbox.heir_y` is the heir's layer (the surface, or a storey above it); `storey()` is 0 on the ground. On a storey `can_step` asks `GamePath.neighbours` (built non-solid cells, no corner cutting), and `climb(-1)` / `climb(1)` go up where the heir stands on stairs and the cell above can be stood on, or down where the cell below is stairs; `build_level` follows the heir. Routes and digging are ground-only (their texts are in `data/world/sandbox.json`), `remember()` does not move the saved place upstairs (the storey is never saved, a visit starts on the ground), and `check_footing()` (each tick) drops the heir to the nearest free ground tile if their floor goes. The actions `world_climb_up` (Q, right stick click) and `world_climb_down` (Z, left stick click) are in `data/ui/input.json`; the screen has Up and Down buttons for touch. `tests/test_game_sandbox_climb.gd` checks.
- **Interiors on foot.** `GameInterior.cells(space_id)` (core) turns a `GameSpaces` interior layout into walkable cells, `{"x,z": floor | door | exit | wall}`: the rooms' tiles are floor, each layout door a `door`, the origin (where the heir comes in) the `exit`, and every tile touching the floor that is not floor a `wall`; `tests/test_game_interior.gd` checks that all 28 interiors are walled in and can be walked across from the exit. `GameSandbox.space` (never saved) is "world" or the interior the heir is in; `use()` (the Use action, F or A, and a bar button) calls `enter()` at a door tile (`door_here()` finds the interior whose door is the heir's tile) or `leave()` on the exit tile. Indoors the heir steps by `GameInterior.passable` (no cutting a wall's corner), the open world's creatures and companions wait, and routes, digging, building and stairs are refused ("Not while indoors."); `remember()` keeps the last open-world place. `TileView.set_interior(id, cells)` draws it (nothing where there is no cell), the screen shows it in full light and hides the world's route, creatures and companions. **People:** `GamePeople` (core; `data/world/people.json`, checked by `tools/check_data.gd`) puts one person in each service interior (forge, temple, store, tavern, board, black market) at a fixed cell of the entrance room; `GameInterior.cells` marks it `person` (solid, drawn in its own colour). Indoors `use()` talks to the person beside the heir (on the exit it still leaves): `GamePeople.talk` returns `{ok, text, open, tab}`, and `open` (`shop`, `workshop`, `tavern` or `board`) is set only when the dynasty's own place is the interior's town and it has the service, otherwise the person only talks. The screen opens that service over the map as a modal (`_open_service`; `ShopPanel.start_tab` picks the tab) and the world waits. The place line names who is beside the heir. `tests/test_game_people.gd` checks. **Towns as ground:** `GameSandbox.move` calls `_arrive()`: stepping onto the ground of a place (`GameSpaces.at_tile`, which today means the four towns with a radius; the wilds have none) makes it the family's place (`d.world.visit`, the first-time line from `life.json` `no_one_walked`, `quests.on_arrive`), with **no years, no arrival event and no dice**; the screen reads `sb.arrived` for its status line. Leaving a town for open ground keeps the last place; nothing happens upstairs or indoors. `tests/test_game_sandbox_arrive.gd` checks. Not built: giving the wilds ground to walk into, the underworld's own ground, travel between realms, and arrival events on foot. The Store tab of the shop panel also sells the healing potion (`_build_potions`, the same `GameDynasty.buy_potion` and price as the life screen's Potion button; `BuyPotion`, shut when the heir cannot pay), so the sandbox's storekeeper sells it too (`tests/test_game_shop_potions.gd`). Not built: people in the family house or in dungeons, people who move or have errands, dialogue beyond a greeting, the underworld's own ground. A dungeon is an interior with contents of its own (see Dungeons).
- **What a room does.** A `room_types` row in `building.json` may have a `use` ({kind, years, hint}; the validator knows only `rest`, years above 0 and at most 1). `GameBuild.room_use(d, x, z)` gives the use of the room a tile is in, and the sandbox's `use()` does it when the heir stands in such a room on the ground floor and no door is there (a door comes first; not upstairs, not in an interior): a bedroom rests, which is `GameDynasty.rest_for(years)` (heal the heir, rest the party, a sickness may come or go, `years` pass; the text game's `rest()` is `rest_for` of a year, the same dice and words). The place line adds the use's hint ("Use to rest."). A forge room (anvil and hearth) has the use `craft` (no years): `use()` returns `{ok, open: "workshop", forge: "home"}` and changes nothing itself, and the screen opens the workshop over the map (`CraftPanel.forge = "home"`; the world waits while a `modal` panel is open, `_modal_open()`). `GameCraft.plan` / `craft` take `forge`: "" is a town's forge (the place's service, as before), "home" is the family's own, which needs no town forge and charges `home_fee_mult` (0.5, in `craft.json`) of the fee. A kennel room (a trough in a room of six tiles or more, `places` in its `room_types` row, at most `max_kennels` of them) gives the family places for creatures: `GameBuild.kennel_places(d)` is added to `GameRanch.extra_pens` and so to `GameRoster.cap`; nothing is saved (the pieces are); its use is `keep`, which says the places and who is kept. `tests/test_game_kennel.gd` checks. `tests/test_game_room_use.gd` and `tests/test_game_forge_craft.gd` check.
- **The open world drawn.** `ui/play/tile_view.gd` (`TileView`, a rendering node) draws the ground as `TileMapLayer` chunks (`tiles.chunk` tiles a side, `tiles.keep` chunks beyond the view, in `data/world/sandbox.json`): each chunk is filled once from `GameWorldGen.tile` and `GameBuild.kind_at`, freed when far from the view, and `refresh_cell(x, z)` redraws a tile after a build or take-down (the screen calls it). A tile's look is its kind (a biome, `water`, or the piece built on it); the atlas is made in code from the `tiles.colors`, except that **the family's built pieces are drawn from full-tile pixel glyphs** (`glyphs` entries named for each piece in `building.json`: stone brick wall, plank floor, cobble road, wooden door, stairs, shingle roof, and the bed, anvil, hearth and trough each on their floor; `TileView.validate` wants no clear pixel in one, `test_built_look` checks), the `homestead` stored screenshot shows a house (a stand-in for sprite art, which replaces `make_tileset` only), and `TileView.validate()` wants a colour for every kind. The sandbox screen keeps a clipped `map` control holding the tile view, an `Overlay` over it (route, creatures, companions, build ghost, heir, touch stick, via `_paint`) and the bar over both; `_sync_tiles` places the view each frame. The movement, pathing and building rules are untouched: the tiles only show them.  `set_level(n)` shows a storey (the screen passes `sb.build_level`): the ground dims by `tiles.below_shade` and that storey's pieces are drawn in a second layer per chunk (`uppers`, a tile only where something is built); `refresh_cell` updates both. **The wilds' look:** a `decor` layer per chunk under `things` draws the ground's tones and decoration and the landmarks' glyphs (`_decor_from`: `GameWildsSites.glyph_at`, else `GameWilds.ground_glyph`), hidden upstairs and absent indoors, covered by anything built and redrawn by `refresh_cell`; a tree is drawn as its biome's look (see The wilds). **Things on the ground:** a second layer per chunk (`things`) draws what stands on a tile over the ground: its node (`GameWorldGen`'s oak and yew trees, herb patches, bone piles, outcrops, unless gathered and not yet regrown, or something is built there) and a shaft dug at the first depth (`dug`), from 8 by 8 pixel `glyphs` in `sandbox.json` (a palette of [r, g, b] or [r, g, b, a]; the atlas tile is clear but for the drawing). The layer is hidden on a storey and absent indoors; `refresh_cell` redraws it. `GameSandbox.dirty` (runtime) lists tiles whose look changed (a node foraged or gathered by a companion, a shaft dug) and the screen redraws and clears them each frame. `TileView.validate` wants a glyph for every node kind and `dug`, 8 rows of 8, palette characters covered. `tests/test_game_tile_things.gd` checks. Still colours and glyphs, not sprite art; no depth view of the underground beyond the first depth. **The world map:** `GameWorldMap` (core; `data/world/worldmap.json`, checked by `tools/check_data.gd`) samples the whole world every `step` tiles (the middle tile of each cell: `GameWorldGen.height_at` below sea level is water, else the biome from `blend`) into a grid of kinds the tile view has colours for, and lists a marker for every anchor (a place the family has not visited is marked but named only "an unvisited place"; the family's place is `here`). `ui/play/world_map_panel.gd` draws it (one pixel a cell in the tile view's colours, scaled; markers, a ring at the family's place, a dot for the heir) as a modal over the sandbox, opened by the bar's Map button, with the world waiting. Pure: no dice, nothing saved. `tests/test_game_world_map.gd` checks. Not built: panning or zooming the map, travelling by tapping it, and showing dug ground or built pieces on it. `tests/test_game_tile_view.gd` checks.
- **Getting away from a fight.** When a creature's contact starts a fight, `GameSandbox._contact()` records on the dynasty where the heir would fall back to (`GameDynasty.sandbox_escape`, runtime only, never saved: `escape_tiles` away on the far side of the creature, stopping short of anything in the way, `_escape_tile`). `finish_battle` keeps it only when the fight was fled from. The next `GameSandbox.start` (the Walk the world screen) puts the heir there and says "gets clear of the fight", then uses it up; after a win or a defeat, or with a fight still on, nothing changes. `tests/test_game_sandbox_escape.gd` checks.
- **A fight on the map.** When `d.battle` is set in the open world the sandbox screen does not swap away: `_open_fight()` runs the battle screen (`BattleView`) as a child of the map under a stand-in app (`ui/play/map_fight.gd`, `MapFight`: the dynasty, `hunt_stopped` always on so no hunt chains, `autosave`/`sound` through the real app, and `show_state()` meaning "the fight is over"). While `_fight` is set the world waits and `_process` does nothing else (so a heir who falls is not cut off mid-result); `_fight_over()` removes the battle screen and the stand-in, calls `GameSandbox.after_fight()` (a fled fight puts the heir clear at once) and leaves the rest (a fallen heir, an ended line) to the next `_process`, which hands on to `app.show_state()`. The creature and the heir are where they were: nothing is re-made. `tests/test_game_map_fight.gd` checks.
- **Guards that fight.** A companion on the `guard` order that reaches the threat it went out to meet gives an `engage` event (`GameCompanions._guard`), and `GameSandbox._guard_fights` settles it with `GameCompanions.duel(d, id, creature_id, tick)`: the companion (a `GameParty._body`, at their own level and hp) fights one foe of that creature (`GameDynasty.foe_for`, `guard_foe_level_mult` times their level) to the end with `GameTactics.auto_turn`, on a `RandomNumberGenerator` seeded from the seed, companion, creature and tick, so the dynasty's dice are untouched and the same fight comes out the same. A win removes the creature from the world and gives the family `guard_gold_share` of its gold; a loss leaves the guard hurt (hp kept on the party member, never below 1) and resting at their post for `guard_rest_ticks` (`rest_until` on the agent: a resting guard goes out to nothing); a guard below `guard_min_hp_frac` of their health will not fight. All numbers and the log lines are in `data/companions/world.json`. `tests/test_game_guard_duel.gd` checks.
- **Loads and the watch.** A gathering companion carries what it gathers (`load` on the agent, not in the stores yet); at `carry_capacity` units, or when nothing is left to gather and it holds something, `haul` is set and `_haul` walks it to the heir and hands it over within `deliver_reach` (`_deposit`: each material into `GameDynasty.stores`, a `delivered` event), then it looks for work again. A new order hands over what is carried at once (nothing is lost), and with no heir in the view a haul is handed over where they stand. The `watch` order (the fifth, after guard; `watch_reach_mult` in `data/companions/world.json`) holds its post like stay by day and by night is a guard with that much longer a reach (`GameCompanions.view` now says `night`); it engages like a guard. `GameCompanions.ORDERS` is the one list (the sandbox's order button turns through it). `tests/test_game_companion_work.gd` checks.
- **Determinism.** All randomness comes from the dynasty's seeded RNG. The same seed with the same commands gives the same result, including after a save and load between rounds. `tests/fixtures/round_baseline.json` is a golden file made by `tests/capture_round_baseline.gd`. Regenerate it only from the commit before a deliberate behaviour change, never to make a failing test pass.
- **World clock.** All passing of time goes through `GameDynasty.pass_time(years)` (ageing, party wages, disease, weather, the death roll, the Ages). Actions reach it with whole years; `GameClock.feed(d, seconds)` (core, no UI) is how a real-time world reaches it: seconds add up to `clock_span_years` spans (`balance.json` "clock_*"), the rest is carried in `GameDynasty.clock_carry` (saved only when above 0), and the clock holds still during a fight, a waiting event or a succession. A new per-year rule belongs inside `_pass_years`, never beside it, so both ways of passing time run it.
- **Replays.** `GameReplay` (core, no UI) records a run as its founding (seed, name, class, bloodline, race, sex) plus the commands given, with a fingerprint of the dynasty (as `to_save()` would write it, and the dice) every `check_every` commands and at the end, and plays it back to prove it. As text it is `GLRP1:` + base64 of the gzipped JSON, one line to paste. A command is `{op, ...}` from `GameReplay.OPS`; each is checked against the game's rules before it runs, so a damaged or hand-made replay is refused with a reason and never crashes. A new way for the player to change the game needs an op here (or it cannot be replayed). The recorder is used by the autopilot (`bot_on`) and the tests; the screens do not record yet. A house founded with hard-mode options writes them in `start.hard` (only then; `begin(..., p_hard)` records them, the autopilot is given none): it must be exactly what `GameHardMode.choices` keeps (only options on, a cap from its list), else the replay is refused with a reason, and it plays as that house, whose fingerprint includes the options. The replay's `version` is `GameSaveVersion.CURRENT` and did not move: the key is optional and old replays lack it, so they play as before; an older build reads a hard-mode replay as a plain house and says where it goes differently. Iron-man does not touch replays (they are recorded runs, not save files). Changing what a command does changes what an old replay plays: that is a version change, and `GameReplay.play` says at which command the run first goes differently.
- **Creature birth.** `GameBirth` (core, no UI, pure functions of data) answers how creatures are born: each creature in `data/creatures/creatures.json` has `born` (`egg`, `live`, or `none` for what is not born and never bred: the undead, constructs, fiends, people-like foes) and, if born, `young` (the name of its young). `GameBirth.mode(mother, father)` says how a pairing's young are born: `kind` is `pure` (one species), `hybrid` (a recipe in `data/creatures/breeding.json` `recipes`, which says for itself how it is born) or `cross` (any other pairing of kin, which follows `settings.mixed_birth_rule`: `mother` by default, or `father`, `egg`, `live`); `young_of` names the young for the parent whose way they follow. The caller says which parent is the mother. A new creature needs `born` (and `young` if born); `GameBirth.validate` is part of `tools/check_data.gd`. Nothing here draws a die or touches the dynasty's state. `tests/test_game_birth.gd` tries all four rules and every pairing.
- **Finding young.** `GameFinding` (core, no UI) rolls whether a dead foe left an egg or young beside it, and `GameRoster` holds what the family keeps (`roster` on the dynasty, saved only when not empty, cleaned on load). The roll uses its own seeded dice (dynasty seed, hunt count, place), never the dynasty's, and the screens call `GameFinding.search_dead` in place of `GamePlague.search` (the battle result and the loot panel); the rules of a life never ask, so autopilot results and the golden digests do not move. Chances, rarity, class and trait bonuses (Wild Instincts, faetouched), the roster cap and the text are in `data/creatures/finding.json`, checked by `tools/check_data.gd`. Two more ways to find young: an event outcome can carry `find: {species: [...]}` (an effect key, validated: born creatures that are not legends; `GameFinding.take` picks one on dice keyed on the seed, generation and event), and the two nest and den events that use it **require the flag `found_young`** (set by the first creature the house takes in), so a house that has never found young is never offered them and the autopilot, which never does, sees an unchanged event pool; and a slain legend that is born may leave its young beside it (`GameFinding.after_battle`, asked by the battle screen's result, once per legend by the flag `legend_clutch_<id>`, `places.legend` times the base chance). The Beast Tamer job has no effect yet: there is no job mechanic (roadmap 60). The Chronicle's Creatures tab (`ui/play/chronicle_panel.gd`, text from `GameRoster.describe`) lists what is kept, with Sell and Set free (see Creature growth).
- **Creature growth.** `GameRanch` (core, no UI) ages the roster as the world clock passes: `GameDynasty._pass_years` calls `GameRanch.on_years`, so every way of passing time runs it. A creature is an egg (egg-layers only), young, adult, elder, then dies of old age; the lengths come from its size class in `data/creatures/ranch.json` (`size_of`, `sizes`), and the stage always follows `age` (saved with `mood`, and re-derived on load). Keeping costs gold a year from the heir (an egg half); an unpaid year sinks `mood`, and at 0 an egg spoils and a creature wanders off. **No dice are drawn** (an elder's end is stretched by a value from the dynasty seed and its id), and with an empty roster `on_years` returns at once, so autopilot results and the golden digests do not move. **The Ranch** is the house's third track (`GameHouse.RANCH`, bought like the others): the `ranch.levels` table in `ranch.json` gives each level its pens (added to `GameRoster.cap(d)`, which is the family's own places plus the pens, so never use the base `roster_cap` alone), a hatchery (eggs cost less to keep and sour slowly) and a nursery (the young the same); `GameRanch.ranch_factor` applies them and level 0 is exactly the old behaviour. A creature can be sold (`GameRanch.sell`, for its size's `value` by stage and mood) or set free (`release`); the Creatures tab asks twice before either. **Work:** grown creatures (an elder at half, none while unhappy, `work.min_mood`) do the work `work_of` gives their species: wool, eggs and venom pay gold each year (paid first, so a working ranch keeps itself), and guards turn away a share of the gold an event would take (`GameRanch.guard_cut`, applied in `GameEvents._apply`, 20% each up to 60%, and exactly nothing with no guards). The species mapping is a stand-in until farm animals exist (roadmap 62). Not built: farm animals (62), moods beyond keep, and party beasts. Raids are below. A new born creature needs a `size_of` entry and every size a `value` (`GameRanch.validate` checks).
- **Breeding.** `GameBreeding` (core, no UI; rules in `data/creatures/breeding_rules.json`, checked by `tools/check_data.gd`) runs from the end of `GameRanch.on_years`, so every way of passing time reaches it. A creature the player sets to breed (`breeding` on its roster entry; adult only) pairs with the first able creature of the opposite sex it is **compatible** with: the same species (`pure`), a species of its own family in `families` (a `cross`, which carries both parents' species in `lines`, is less fertile and likelier sterile) or a pair `GameBirth.recipe_for` knows (`hybrid`; the recipe's optional `species` is what is born; none ship yet, they need creature data and art). Each whole year the world clock crosses, each pair rolls on dice keyed on the dynasty seed, the year and the two ids, **never the dynasty's**: nothing in a life moves, and a ranch that breeds nothing does nothing. How the young are born is `GameBirth.mode` (the cross-breed rule); young keep the mother's species and `line`, inherit traits from either parent (`trait_pass_chance`, at most `max_traits`) and can mutate one; the mother rests (`cooldown`). Traits (`hardy`, `sickly`, `fierce`, `prized`, `industrious`, `fruitful`) change keep, price, work, guarding and fertility through `GameBreeding.trait_mult`. Roster entries gained `traits`, `breeding`, `cooldown`, `sterile`, and for bred young `bred`, `parents`, `line`, `lines`; all load cleaned (`GameRoster.load_list`). Not built: choosing pairs, hybrid species and their art, naming lines, and young going out with the party.
- **Creatures of the realms.** `GameRealms` (core, no UI; `data/creatures/realms.json`, checked by `tools/check_data.gd`) gives every creature a realm: `of` lists the creatures that are not of the home realm (`settings.home`, the Material Realm; unlisted means home). **What is live:** a creature of another realm sells for `foreign_value_mult` at home (through `GameBreeding.trait_mult`, which ends with `GameRealms.mult(e, key)`; `GameRanch.yearly_keep` asks it too). The worlds are joined by **gates**, one per realm but home: `gate_open(d, realm)` is true for home and otherwise when the flag `gate_<realm>` (`settings.gate_prefix`) is set, and `open_gate(d, realm)` sets it once and returns the line to tell ("" after). `move(d, id, realm)` takes a kept creature to a realm (`in_realm`) only through the open gates of the realm it leaves and the one it enters (`why_not` gives the text); there it is unsettled (`unsettled`: dearer keep, faster souring, less work and young) until it has lived there the realm's `adapt_years` (`adapt`, then `settled`), unless the realm is its own. `cross(mother, father)` says what young of two realms carry (`realms`, the mother's first, and `marks`, at most `max_marks`); `on_birth(d, e, mother, father)` (from `GameBreeding._birth`) writes it only when `settings.linked` is on and both gates are open. A mark multiplies the same numbers a trait does (`MULT_KEYS`); an unstable realm's mark (the Void, the Dreaming) is awake or `dormant` by the year (`awake_in`: dice keyed on the seed, year, creature and mark, never the dynasty's). `on_years` (called at the end of `GameRanch.on_years`) adapts and flickers, and returns at once for a roster with no `in_realm` and no `marks`. Gate flags are story flags, so they save with `flags` and nothing else changes. **The Verdant Court** has three creatures (`of`: verdant, mark glamoured): the thornhound (live-born, `forest`/`fae`, a guard, pack-like), the moss stag (live-born, a grazer, `herd`/`skittish`/`territorial`: hostile in the data as every wild creature must be, but it runs), and the glimmer moth (egg-laid, a flier, low threat, `fae` only, so no forest hunt meets it). On the balance harness's seeds 1 to 3 the autopilot stood in a forest or fae place only in generations 1 and 2, so its lives never meet the stag or the hound (minimum generations 5 and 10) and the harness cannot see them. The **Standing Stones** event (`verdant_stones`, Elderglade, once, needs the flag `fae_danced` that dancing in the fae ring sets) has the outcome `gate: verdant`, which `GameEvents` applies with `open_gate` and tells. Tests that change the data restore `GameRealms._cache`. A new creature of another realm goes in `of`; a new realm needs a mark of its own and a gate is implied (every realm but home). **Realm time:** each realm has a `flow` in `realms.json` (its years for each year at home: 1 at home, 0.5 in the Verdant Court and the Dreaming, 0.75 hollow, 1 Dragon Isles, 1.5 Elemental, 1.25 Clockwork, 0.25 the Void; the validator wants 0.25 to 2 and home at 1). `GameRealms.flow(e)` is the pace of the realm a creature is kept in, 1.0 at home, and `GameRanch.on_years` ages, feeds and works a kept creature by it (`_live_years` gets `years * flow`, mood change and keep cost scale, `yearly_work` is multiplied) and `GameRealms.on_years` adapts it by the realm's own years; at flow 1 every number is exactly what it was, so nothing at home moves. Not scaled: breeding cooldowns and gestation (still home years). `tests/test_game_realm_time.gd` checks. **Not built:** gates for the other realms (their flags are read, nothing opens them), a screen that moves a creature (so `move` is reached only from code and tests), a screen that shows a creature's realm or its flow, and cross-realm pairs outside the breeding families.
- **Subclasses.** `GameSubclass` (core, no UI; `data/subclasses/subclasses.json`, checked by `tools/check_data.gd`) is a calling layered on the heir's class: none or one (`GameHeir.subclass`, saved with `subclass_founded` only when there is one, an unknown id loading as none), never replacing the class's skills. It is **picked at the founding** (`GameDynasty.new_game`'s last argument, the title screen's pick, `GameApp.new_game`), **taken later** by the living heir for gold (`GameSubclass.take`; the price scales with the generation, a change costs double), or **passed to a child** (`GameSubclass.on_succession`, called from `choose_heir`, 50%, on dice keyed on the seed and the child, never the dynasty's). One chosen at the founding or inherited is *founded* and its perks are stronger (`founder_scale`); one taken later is at plain strength. A perk is a multiplier on a number the rules already have, read through `GameSubclass.perk(heir, key)` (1.0 with no subclass, so nothing moves without one, and every read multiplies by it **after** the number's own dice are drawn, so a house with none plays bit for bit as before). A new perk is a key in `perks` (with its words) plus a place that reads it; `tests/test_game_subclass_roster.gd` fails on a perk no calling gives or no place in `core/game/` reads. **Twenty callings** (`price_mult` scales what each costs to take): the Tamer, Runescribe, Armorer, Bladewright, Enchanter, Alchemist, Artificer, Gemwright, Hidewright, Trapsmith, Spiritbinder, Wildcaller, Feastwright, Wayfinder, Delver, Stonewright, Greenwarden, Steadholder, Caravaneer and Venomwright (the validator refuses the generic names Magic Crafter, Scroll Master, Item Crafter and Blacksmith, a repeated name, and a perk nobody gives). **Perks and where they are read:** creatures `find_mult` (GameFinding.chance), `keep_mult` (GameRanch.yearly_keep), `fertility_mult`, `mutation_mult` (GameBreeding), `value_mult` (GameRanch.sell_price); the forge `forge_fee_mult` (GameCraft.plan, brew_plan and GameSubclass.work_plan), `craft_quality_mult` (GameCraft.quality), `salvage_mult` (GameCraft.salvage_yield, which now takes the heir), `brew_yield_mult` (brew_plan's `makes`), `gather_mult` and `essence_mult` (GameCraft._roll_drops: the same dice, more of the haul or a likelier essence); the shops `buy_mult` (GameItems.price_mult) and `sell_mult` (GameItems.sell_price); loot `drop_mult` and `rarity_mult` (GameLoot.after_search and after_legend: a lower bar on the same roll, a stronger boost); mining `ore_mult`, `dig_mult`, `cave_mult` (GameMine.dig, hazard_chance); `build_cost_mult` (`GameBuild.cost_of`, which place and the cost check use; a refund is a share of what the family paid, so pulling down cannot gain); `farm_mult` (GameFarm.yield_mult), `forage_mult` (GameForage.forage), `haul_mult` (GameCompanions gather), `train_mult` (GameDynasty.train), `work_mult` (work), `hunt_gold_mult` and `hunt_xp_mult` (finish_battle), `raid_mult` (GameRaids.chance), `carry_mult` (GameCarry.capacity), `disease_mult` (GameDisease._expose, for the heir); and the heir's fights `attack_mult`, `spell_mult`, `defense_mult` (GameHeir.attack_power, magic_power, defense), `potion_mult` (GameBattle.use_potion) and `flee_mult` (GameBattle.flee, never above 95%). **Works:** each calling has its own items, forty in all (two or more each), which are ordinary gear in `data/items/items.json` with a `subclass`, a `recipe` {cost, fee, min_level} and **`"shop": ""`**, so no shop stocks one and the autopilot (which takes no calling and never calls `GameSubclass.make`) never meets one. `GameSubclass.work_plan` / `make` (the craft panel's "works" section and the Chronicle tab's list) make one for the materials in the stores and the fee (`forge_fee_mult`, the Smithy and the home forge's share apply) at a town forge or the family's own, only by that calling and at its level, once if it is gear; no dice. A weapon needs a kind in `feats.json` and a weapon or armour a look in `data/art/gear.json`, as any item does; the validator also refuses a work that is sold, unique, of an unknown calling or without a recipe. Five callings (Tamer, Alchemist, Feastwright, Greenwarden, Venomwright) also have a brew of their own (`calling_brews` in `craft.json`, read by `GameCraft.brew_plan` and listed by `calling_brews(heir)`, never by `brews()`). A replay's `start` keeps the founding calling (`subclass`, written only when one was chosen, checked on reading). The Chronicle's Subclass tab takes one, shows the works of the current calling and each other calling's perks; the life screen names it after the class. Not built: advanced subclasses of the Tamer, a full class born to a calling, and the replay's commands do not record taking a calling later. Tests: `test_game_subclass.gd` (the mechanic), `test_game_subclass_roster.gd` (the twenty, their data, breaks, the shops, the autopilot), `test_game_subclass_perks.gd` (each perk's effect and that none is exactly 1) and `test_game_subclass_works.gd` (every work made, every refusal, wearing, saving, the screens). **Balance (docs/BALANCE.md, Subclasses):** `balance_harness.gd -- subclass=<id|all|none> [keep]` founds the dynasties in a calling (`keep`: every heir carries it, the number to read) and `long_run_check.gd` takes `subclass=`; twenty callings x 12 seeds x 8 races x 10 generations showed no calling out of line beyond noise (about 1 point of battle deaths per row) except the Wildcaller, whose `train_mult` 1.1 opened Hard hunts early (4.5% against 3.1% on 36 seeds; now 1.04, 3.1%). The Tamer, Artificer and Delver have no perk the autopilot reaches (their runs equal the baseline's digit for digit), so their perks are judged on paper; `test_strength_bands` holds founded perks to 0.4-2.0x and fight/training perks to 25%. Retune a fight, training or hunt perk only with `subclass=<id> keep` on 36 or more seeds. The Trapsmith's `hunt_gold_mult` went from 1.08 to 1.05 (gold at death +11.9% -> +6.9% on seeds 13-36; the Hidewright's -11% was noise): docs/BALANCE.md, *Gold gaps*, and the plan for the perks the autopilot cannot use is there too.
- **Item and material list.** `GameMaterials` (core, no UI; `data/items/materials.json`, checked by `tools/check_data.gd`) is the one list of materials (id, name, tier, tags, `weight_mult`, `price_mult`). Every item in `data/items/items.json` names a `material` and a `weight`; its tags are the material's plus its slot or kind and any `tags` of its own (`GameItems.tags_of`, `has_tag`, `material_of`, `weight_of`). A new item needs a listed material and a weight (the validator checks, and that gear does not stack and consumables do); a new material needs a tier, tags from the list at the top of the file and use by an item. Harvesting, mining, crafting and the loot generator are meant to extend this list, not make another.
- **Creature behaviour.** `GameBehaviour` (core, no UI, no screen yet; `data/creatures/behaviour.json`, checked by `tools/check_data.gd`) is how creatures act in the open world, **by tag, not by code**. Each creature lists tags (`creatures`); each tag `set`s some of the `defaults` parameters; the global `order` decides which tag wins when two set one, so the order a creature lists its tags does not matter (`params` caches, so tests that change the data must clear `_params`); `pack` is never listed, it comes from `swarm` in `creatures.json` (`is_pack`). `step_all(agents, view, seed_value, tick)` is the one state machine and returns new agents (inputs untouched): `view` is `{targets: [{x, z}], night, walkable: Callable(x, z)}` (`world_view(d, targets, night)` builds one from `GameWorldGen`: ground creatures keep off water, fliers do not). An agent (`new_agent(uid, id, x, z, hp)`) has a mode (`MODES`: idle, wander, chase, flee, return, herd, dead), a home and a heading. Rules: chase needs `hostile` and a target within `sight` (times `sight_night` or `sight_day`; keeps a target out to `lose_sight_mult` times that); `leash` (from home) ends a chase and sends it home until within half the leash; `guard_radius` makes it fight only targets within that of home; flee when hurt below `flee_hp` or `skittish`, until `flee_dist` away; an ambusher (`ambush_range`) stirs only for a close target and bursts at `ambush_speed_mult` for `ambush_ticks`; a pack animal that sees a target alerts its kind within `alert_radius` and the pack takes bearings `flank_spread` apart round the target; herds keep within `herd_radius` of their centre. Every die is `_u(seed, uid, tick, tag)` (a hash of strings, never the dynasty's `rng`). A new creature needs a `creatures` entry (the validator checks every creature has one, every wild one is hostile, every tag is used, and that a guard post is not wider than the leash); a new behaviour is a new parameter in `defaults`, a tag that sets it, and a branch in `_act` with a test. `night` is a flag the caller gives (`GameDay.is_night`, item 51, is the open world's). Not built: a tick loop that spawns and despawns, combat in the open world, pathfinding round obstacles (item 49).
- **Pathfinding.** `GamePath` (core, no UI, no screen yet; `data/world/pathing.json`, checked by `tools/check_data.gd`) is A* over 3D cells: the surface at layer y = -1 (one cell per `GameWorldGen` tile, via `world_ground(d, built)`) and dug cells at y >= 0 from `GameMine`. A `ground` is `{surface: Callable(x,z)->{h,water,biome,block}, dug: Callable, built, max_depth}`, so tests build small grids. Movers (`walker`, `climber`, `swimmer`, `flier`) set climb, drop, water and block rules; terrain, slope, diagonal and `up_mult` costs are data; diagonals never cut corners. `built` is an overlay `{"x,y,z": kind}` (wall solid; floor, road, door walkable; a floor over water is a bridge), by default the dynasty's own `built` (item 50; pass one to `world_ground` to replace it). `find` returns `{found, path, cost, expanded, partial}` and, when bounded by `max_nodes`, the way to the nearest cell reached. The heuristic uses the ground's cheapest step (`_floor_cost`), so it stays exact; `tests/test_game_path.gd` compares with Dijkstra. `GamePath.router(ground, mover)` is a Callable put in `GameBehaviour`'s `view["router"]`: chase, return and herd steer for the next cell instead of the goal; no router means item 48's behaviour exactly. Pure: no dice, nothing saved. **Path cache:** `GamePath.new_cache()` / `cached_router(ground, cache)` remember the next tile for each (mover, from, to), so a crowd heading for one goal pays for one search a tile; `sync(cache, d)` clears it when `ground_stamp(d)` (the built pieces and the mine, hashed) changes, and `cache_max` (`pathing.json`) holds it down. `GameSandbox` keeps one (`path_cache`, `path_line()` for a readout) for its companions, synced every tick. The answers are the plain router's exactly (`tests/test_game_path_cache.gd` checks). Not built: a pathing screen (the readout line exists but nothing draws it), caching whole routes, creatures using the router.
- **Building.** `GameBuild` (core, no UI, no screen yet; `data/world/building.json`, checked by `tools/check_data.gd`) is where and what the family may build. The family house is the first base: `claim_radius(d)` is `base_radius` round `base_place` (a town anchor) plus `radius_per_house_level` for every level of every `GameHouse` track, and nothing is built outside it. A piece is one of the four kinds `GamePath` walks (`wall`, `floor`, `road`, `door`; the validator wants both lists to match) with a `cost` in stores materials, `gold`, `refund`, `max_slope`, `over_water` and `needs_frame`. `check(d, kind, x, y, z)` returns why not or "" and `place`/`remove` return `{ok, text}`: one piece per cell, not on a `block` tile (tree, outcrop), slope to a dry 4-neighbour within `max_slope`, over water only an `over_water` piece that `_bridge_ok` joins to shore within `max_span` tiles through built pieces, a door needs walls on two opposite sides (`_framed`), underground only a `GameMine.is_dug` cell, y from -1 (surface) to the mining `max_depth`. `remove` refuses a wall a door hangs on and a plank another rests on. `rooms(d)` fills four-way over the surface from the built pieces' bounding box: closed regions (not touching the box, no open water, at most `max_room_area`) with `area`, `doors` and `sealed`. `GameDynasty.built` is `{"x,y,z": kind}`, saved only when not empty and loaded clean by `GameBuild.load_state` (bad keys, unknown kinds, out-of-world cells dropped); `GamePath.world_ground(d)` uses it. All text is in `building.json`. Pure: no dice; the autopilot builds nothing (`tests/test_game_build.gd` checks). Tests that change the data reset `GameBuild._cache`. Furniture (`bed`, `anvil`, `hearth`, `trough`: pieces marked `inside`) is built only on the surface in a `room_at` room, and is solid in `pathing.json` (the validator wants that). `room_types` in `building.json` names a room by what stands in it (`room_type(d, room)`, first type whose `needs` and `min_area` fit wins, so most demanding first; `room_line(d, x, z)` is the sentence the sandbox status shows). Taking the furniture away takes the name away; nothing else is stored. `tests/test_game_build_rooms.gd` checks. Storeys: a piece may stand above the ground at y = -1 - n (`top_y()`, `max_storeys`); `supported(d, x, y, z)` wants a wall or stairs below it on the ground floor (`ground_bearers`) or a room under it, and a wall, floor or stairs higher up (`upper_bearers`); `remove` refuses what would leave a storey piece hanging (`all_supported`). Stairs (`stairs: true` in both building.json and pathing.json, the validator wants them to agree) go on or above the ground, not on the top storey, and `GamePath` climbs them (a stairs cell leads up to the cell above it if that can be stood on, and down again). `GameSandbox.build_level` (not saved) is the storey the build controls work on; the screen has a Level button. `tests/test_game_build_storeys.gd` checks. **Roofs and upper rooms:** `roof` is a piece (`roof: true`) that goes only on a storey, one layer above the top storey allowed (`top_y() - 1`; no other piece may go there), rests like any storey piece, bears nothing (the validator refuses a roof among the bearers) and is solid. `rooms_on(d, y)` finds rooms on any layer (`rooms(d)` is the ground's, `rooms_all` every layer's): on a storey a room is walls and doors round a region whose every cell holds a floor, stairs or furniture. Each room has `y` and `roofed` (a `roof_covers` piece, roof or floor, over every cell); `room_line`, `room_at` and `room_use` take a layer, furniture goes on an upper floor in its place (taking it down leaves the floor), the kennel count and the summary use `rooms_all`, and the sandbox's Level button has one more step, the roof layer (`level_name()`). `tests/test_game_roofs.gd` checks. **Damage and repair:** `GameRepair` (core; `repair` block in `building.json`) keeps `GameDynasty.damage` ({"x,y,z": level}, saved only when not empty, loaded clean against the built pieces). `hurt` damages a piece a level; at `max_damage` it is wrecked and `GameBuild.collapse` drops whatever then hangs (storey pieces, doors); a damaged roof does not cover its room; `repair` costs `repair_share` of the piece's cost per level (gold for a road); `remove` clears damage. A fifth raid kind, **vandals** (`takes: "pieces"`, event `raid_vandals`), applies only with built pieces and hits `vandal_hits` of them on dice keyed on the seed (`GameRaids.defend`), and each built piece adds `built_piece_value` to `house_value`, so builders are raided more; the autopilot builds nothing, so no balance change. The screen has a Repair button (`GameSandbox.repair_at`). `tests/test_game_repair.gd` checks. Not built: damage from weather or fights, repairs by companions, what a roof does beyond covering.
- **Spawn tables.** `GameSpawn` (core, no UI; `data/creatures/spawn.json`, checked by `tools/check_data.gd`) says which creatures appear where and when. **`hunt_pool(era, place_biomes)` is the pool a text-game hunt draws from**, moved out of `GameDynasty.start_hunt` unchanged (creatures of the era whose biomes meet the place's, fallbacks included, **in `GameData.creatures` order, because the hunt picks by index with the dynasty's dice**): changing what it returns, or its order, changes every seeded fight (a balance change); `tests/test_game_spawn.gd` compares it with a copy of the old code. The rest is for the world and draws no dice of the dynasty's: `table(context)` (context from `GameSpawn.context(surface, depth, era, season, weather, night, place)`) gives `[{id, weight}]` sorted by id for a surface biome, an underground depth, or an authored place (the place's own `hunt_pool`); `weight_of` is the creature's weight times its `seasons`, `weather` and `night` multipliers; `pick` chooses by weight from the caller's dice; `context_at(d, x, y, z, night)` builds the context for a tile of `GameWorldGen` (y is -1 on the surface, else the depth: open water, a town's ground and the soil above the stone have none) and `spawn_at` rolls a creature on dice keyed on the seed, tile and slot. Each creature's `surface` biomes must be surfaces of its own `biomes` (via `worldgen.json` `surface_of`) and its `depth` band needs an underground biome (the validator checks, and that every wild creature has an entry and lives somewhere); a new wild creature needs an entry here. `night` is a flag the caller passes (`GameDay.spawn_context` passes the open world's). Hunts do not use the weights yet. Not built: hunts using season, weather and night, packs and elites in the world, caps and despawn.
- **World generation.** `GameWorldGen` (core, no UI, no screen yet; `data/world/worldgen.json`, checked by `tools/check_data.gd`) is the sandbox's surface as a pure function of `seed_value` and a tile, so it saves nothing and draws no dice. The **authored map is the skeleton**: each place in `data/world/world.json` is an **anchor** (`GameWorldGen.anchors()`, at x and y times `scale`, in the biome `surface_of` gives its first mappable biome), and the generator never moves or contradicts one: the border warp in `blend` fades to nothing at an anchor (`anchor_lock`), and towns and dungeons are flat, dry and node-free inside `anchor_radius` (`in_anchor_ground`, `height_at`). Between anchors `blend` gives the biome (nearest anchor after the warp) and a base and amp blended from the nearest few; `height_at` adds fractal noise, flattens at anchors and pulls the edge of the world under the sea; `node_at` places a node from the biome's `nodes` table and a clumping noise (an **outcrop** only where `GameMine.ore_at` finds ore within `outcrop_depths` of the surface, and of that ore); `tile` and `chunk` assemble them. Noise comes from `_lat`, an integer mix: **do not use Godot's `hash` of nearby integers for a new roll here, it is correlated between neighbouring tags** (it left forests without herbs). A new place needs a biome that has a `surface_of` entry and a position on the map; a new node kind needs an existing material (or `""` for an outcrop) and an entry in a biome's table (the validator checks). `tests/test_game_worldgen.gd` checks the anchors, the seed, the land, the sea, the nodes and that nothing of the dynasty's moves. **Water:** `settings.water` in `worldgen.json` lays lakes, rivers and fords over the land (`_water`, called by `_surface`, so everything below reads it through `tile`, `height_at`, `body_at`, `water_at`). A tile's `body` is `""` (dry), `sea` (under the sea level, as before), `lake`, `river` or `ford`; `GameWorldGen.is_water(body)` is sea, lake or river, and a **ford is shallow water a walker can cross** (`water` false on its tile, drawn as `ford`). **Rivers** follow the zero-crossings of a large noise field (`river_scale`; a river is where it crosses 0.5, `river_width` either side), only where a second noise says the land is wet (`wet_*`), thinning to nothing as the land rises from `river_fade_from` to `river_fade_to` (they start in the hills), with a valley carved beside them (`valley_width`, `valley_depth`; never carved under the sea). **Lakes** fill the basins of a third noise on low ground (`lake_threshold` with a `lake_band` ramp, `lake_depth`, `lake_land_max`), going under the sea level where deep; a tile's `depth` is how far a lake's bed lies under its banks (0 elsewhere), which `GameRelief.kind` reads (`lake_deep` or more is drawn deep). **A lake's rim is land, never a sea pit**: land that is not lake is held at the sea level or above (a ring of sea round a swampy town once cut Mirefen off on seed 14), and a river's or ford's bed is too. A river is a ford where a fourth noise is high (`ford_threshold`). **Nothing within a town's or dungeon's reach of an anchor** (`clear_inner` plus its radius, fading in by `clear_outer`) is water, so every place stands on dry ground. **Roads:** `GameWorldGen.roads()` is every link of the text game as a straight line between its two anchors (`road_distance` is how far a point is from the nearest), and where a road crosses a river or a lake the water is a ford `road_width` either side, raised to the sea level (a causeway). **This is what keeps the land joined**: with fords from noise alone 7 of 24 seeds left a place cut off from Hearthmere (a flood fill over the whole world, by the walker's own climb and drop), with the roads' causeways none of 60 do; a change to the water settings or to which tiles are water needs that check again (`tests/test_game_water.gd` floods two seeds; sweep more by hand). A ford, a river and a lake are one body to the pathing (`GamePath.world_ground` asks `water_at`), so creatures and companions cross a ford and keep to the bank otherwise; the world map shows seas and lakes but not rivers (narrower than a cell). Building over a river or lake follows the old bridge rules. Not built: boats or swimming for the heir, fish, flowing water or floods, rivers that run to the sea (they follow noise, not slopes), waterfalls, and the node, spawn and map rules knowing a river from a lake. Without water, the walker already cannot reach Whisperwood on seed 77: its forest's trees wall it off (a tree or rock outcrop blocks a walker); that is the forest, not the water.

- **Relief.** The land's height is already in `GameWorldGen` (every tile has a `height`, the sea takes what is under `sea_level`, a walker climbs 2 and drops 5 a step, a building wants level ground), and `GameRelief` (core, no UI; `data/world/relief.json`, checked by `tools/check_data.gd`) is how it **shows**. `step_at(d, x, z)` is a land tile's light step from -`steps` to `steps` (the sun in the north-west: a tile rising to its east and south is brighter, one falling away darker, `slope_k` a step for each height of difference; high ground lighter than low by `alt_gain` across `alt_span`; a flat valley is a little dark); water has none. `kind(tile)` is what a tile looks like before anything is built on it: `deep` where the bed is `deep_depth` or more under the sea, else `water`, `snow` on `snow_biomes` ground at or above `snow_line`, else its biome (`TileView.kind_for` asks it). - **The wilds.** `GameWilds` (core, no UI; `data/world/wilds.json`, checked by `tools/check_data.gd`) is how the open world's ground **looks** beyond the land: pure functions of the seed and a tile, drawing no die of the dynasty's and leaving `GameWorldGen.tile` (height, water, node) exactly as it was, so the guarantees of the land (flat dry towns, reachable places, the water tests) hold. Each surface biome has `tones` (translucent patches) and `decor` (tufts, flowers, reeds, boulders, snowdrifts, lava cracks...) rows of a probability a tile (`clump`, `near` water, `min_h`/`max_h`) and `trees`, the glyph a tree node is drawn with in that biome (`GameWilds.node_look`: a birch, a pine, a willow, a dead tree, a giant fungus; the node is still the same oak or yew to gather and `TileView._thing_from` draws the look), and each body of water has marks of its own. **Areas:** each `wilds` place of `world.json` has an entry in `areas` (`radius`, its own tables, a `ring` of standing stones, a `lattice` of hedged fields, `placement` and `fixed` landmarks); `area_at(x, z, biome)` gives its strength (1 to `area_fade` of the radius, fading to nothing, only on the place's own biome), a tile takes the area's tables where a keyed roll is under that strength, and `area_of` is the id spawns, landmarks and loot use ("" is generic land). `thin(x, z)` takes decoration away inside a town's, plot's or dungeon's ground and margin and cuts it to `road_floor` on a road. A new glyph is data (8 by 8, a palette; its id must not be a kind the tile view already has) and `TileView.kinds()` appends `GameWilds.glyph_ids()`; the validator checks every row, tree look, area, landmark and that no two areas look the same. **Landmarks:** `GameWildsSites` (core, no UI) cuts the world into cells of `cell` tiles each holding at most one of `placement` (by biome, or the area's own) on dry, node-free ground clear of towns, plots and dungeons (`_spot_ok`), plus each area's `fixed` ones at an offset from its anchor (found by a search round the offset; Elderglade's fae ring is at its anchor, Whisperwood's lair only because `world.json` gives it a `lair`); an id is `lm:x:z`. `glyph_at` draws a landmark's layout under the nodes, `within`/`near` find them, and **the dynasty's `wilds`** (`{found: [ids], used: {id: {gen, n}}}`, saved only once set, loaded clean by `GameWildsSites.load_state`) records what the heir has come within `see_range` of (`discover_near`, called by `GameSandbox.refresh`, logged) and what has been used. `GameSandbox.use()` (when no door or room use applies) uses the landmark within `use_reach` (`GameWildsSites.use`): an outcome drawn from the kind's `outcomes` on dice keyed on the seed, the landmark id and its use count (gold scaled by the generation, XP, healing, a small hurt that never kills, a potion, ore or herbs into the stores, loot), once until `renew_gens` generations pass; a trader (`trade`) opens the **merchant panel** (see below) instead. The place line says what Use will do. No dice of the dynasty's; the autopilot never walks the wilds. `tests/test_game_wilds_trade.gd` checks. Not built: landmarks that start fights or open a dungeon's door (a cave only names the dungeon near it; specified in `docs/WILDS_ENCOUNTERS.md`), creatures that live at landmarks, sprite art for the glyphs, and the world map showing the ground's look.

- **World events.** `GameWorldEvents` (core, no UI; `data/world/world_events.json`, checked by `tools/check_data.gd`) is the wars, famines, pestilences, fairs and golden ages that come and go. One runs at a time: `GameDynasty.world_event` is `{id, began, until}` while one runs or `{id: "", until}` while the world rests after one (saved only when not empty, loaded clean by `load_state`). `on_years` (called from `_pass_years` right after `world.advance`, so every way of passing time reaches it) ends a running event at its `until`, rests `rest_years`, and for each free whole year rolls `rolled(d, year)`: nothing in the first `grace_years`, else `chance_per_year`, picked by `weight` among the events whose `min_gen`/`max_gen` window holds `era_gen()`; `length` picks its years. **Every die is keyed on the seed and the year, never the dynasty's**, so the rest of a life draws exactly as before. - **Day and night.** `GameDay` (core, no UI, no screen yet; `data/world/daycycle.json`, checked by `tools/check_data.gd`) puts a day on the world clock. `GameDynasty.world_seconds` (saved only when above 0, loaded clean by `GameDay.load_seconds`) is added to by `GameClock.feed` only while the clock runs; a day is `day_seconds` of it (an abstract rhythm, not tied to the length of a year) from `start_phase`. `phase` is 0 at midnight and 0.5 at noon, `sun_height` is `-cos(2*pi*phase)` and `sun_light` ramps 0 to 1 across `twilight` either side of the horizon, so `phase_name` is night, dawn, day or dusk; `is_night` is the sun's light under `night_below` (weather never makes a night). **The weather is the world's own** (`world.weather_id`, rolled each span with the dynasty's dice by `GameWorld.advance`, and what battles use): `weather_look` gives each weather a `light` share, `fog`, `precip` (none, rain or snow) and `sight`; every weather in `world.json` needs one (the validator checks). `look(d)` is `{phase, hour, sun, light, tint, fog, precip, weather, season, night}` for a renderer. `view(d, targets)` is `GameBehaviour.world_view` plus `sight_mult`, which `step_all` multiplies into how far a creature sees (absent means 1, so every other caller plays as before), and `spawn_context` is `GameSpawn.context_at` with the current night. - **Mining.** `GameMine` (core, no UI, no screen yet; `data/mining/mining.json`, checked by `tools/check_data.gd`) is the ground as data: a **site** (a place id) has rock **layers** (hardness, whether ore forms), three **zones**, and **ore veins** (each `block`-sized cube may hold one vein, a sphere picked from depth `ores` bands by weight and `chance`; `ore_at` looks at the 27 nearby blocks), all a pure function of `seed_value`, the site and the cell, so the same seed gives the same ground and no dice are drawn. Depth y counts down from 0; `age_at` says which Age a depth is (digging goes back in time). **Digging** (`can_dig`, `dig`) needs open air beside the cell (any cell at depth 0, otherwise a dug neighbour), costs `effort` (hardness times the stage's `hardness_mult` over Strength) and puts ore into `GameCraft` stores. Each dig adds strain to its `region` (more the deeper); `stage_of` gives the stage (softer rock, fatter veins through `ore_bonus`, read by `ore_here`) and the last stage (`gateway_stage`) records a **gateway** at the cell that tipped it. `GameDynasty.mine` is `{site: {dug: {"x,z": [[y0,y1]]}, strain: {"rx,rz": f}, gateways: [...]}}`, saved only when not empty and loaded clean by `GameMine.load_state`. A timber prop (`prop_cost` of `prop_material`, from the stores) takes the weight, else the heir loses `hazard_hp_pct` of their health and is never killed (left on at least 1). `tool_bonus`: each `tool_levels_per_ore` levels of the Smithy add an ore to a strike. No dice. - **Carry limits.** `GameCarry` (core, no UI; `data/items/carry.json`, checked by `tools/check_data.gd`) is how much the heir can carry: `capacity` is `base_capacity` plus `per_strength` times Strength, `carried` is the weight (item 42) of the pack, what is worn and `potion_weight` per healing potion. `GameCarry.can_carry` gates the voluntary pickups: `GameItems.buy` refuses (`why_not` gives the line), and `GamePlague._find` and `GameLoot._give` sell what does not fit where it lies (`sell_find`). `GameDynasty.give_item` (events and quests) always takes, so a heir can be over the limit (`burdened`); there is no other penalty yet. `GameCarry.drop` leaves one item from the pack (never worn gear); the pack screen's Drop button asks twice for gear. - **Loot generator.** `GameLoot` (core, no UI; `data/items/loot.json`, checked by `tools/check_data.gd`) builds items that are in no list: an item **is its id**, `gen:<rarity>:<slot>:<form>:<material>:<affixes joined by +, or ->:<mythic or ->:<grade>:<quality 0-9>`, and `GameLoot.build` rebuilds it from the forms, `GameMaterials`, affixes and rarities, so a save holds only the id (a damaged or unknown id builds nothing and loads as an unknown item). `GameItems.item_def` returns the built item for a `gen:` id, so everything that reads items (wearing, selling, `tags_of`, `GameFeats.weapon_kind`) works unchanged. **It grows with the world**: `tier_ceiling(gen)` opens material tiers by generation (`tier_gens`), `grade_of(gen)` adds +1 every `grade_gens` generations after the top tier (up to `max_grade`) and strengthens every effect. Rarity is a weighted roll out of `weight_total` (a million; mythic is 10); a rarity may reach `overreach` tiers above the ceiling. **Drops are asked for by the screens**, never by the rules of a life: `GameLoot.search_dead` (the loot panel and the battle screen, in place of `GameFinding.search_dead`) rolls once per foe on its own dice (`drop_chance`) and `after_legend` gives a slain legend one drop at the legend boost, once per legend by a flag, so the autopilot (`GameBot` never calls them) and the golden digests do not move; `tests/test_game_loot.gd` checks that an autopilot life meets no made item. A new form, affix or mythic is data (the validator checks stats, slots, tags and that every slot has forms, tier 1 prefixes and suffixes, and a mythic); a new stat an affix uses must be in `items.json` `effect_labels`. Made gear has no art yet (it keeps the old block look). Not built: scrapping, drops from events and chests, and crafting on the same parts.
- **Raids.** `GameRaids` (core, no UI; `data/creatures/raids.json`, checked by `tools/check_data.gd`) is asked by `GameDynasty._pass_years` (after `GameRanch.on_years`), so every way of passing time reaches it. A house can be raided if it has **something worth taking**: animals in the pens, or a house that has been built (`house_value`: `house_value_share` of what each track's levels cost). A plain house is a target too once the heir holds `plain_min_gold` (`has_purse`), but only a small one: with no animals and nothing built the chance is the flat `plain_chance` a year whatever the purse holds (a purse that scales the chance would be a raid every year for the autopilot, which holds thousands, and each raid pays XP); with no purse either, the chance is 0 and nothing is rolled. This **was a balance change**: the autopilot holds gold, so it now meets about 0.8 raids a life, and the five autopilot-life digests in `tests/fixtures/round_baseline.json` were recaptured (every fight scenario is unchanged); see PR for the before and after harness numbers. Each whole year the clock crosses rolls on dice keyed on the seed and the year, **never the dynasty's**; the chance is `base_chance` plus `per_stock_gold` times the `valuables` (stock plus house), capped at `max_chance`, and cut by `deterrence` (the guards, `GameRanch.guard_cut`, up to `deter_share`; no animals, no guards, until hired guards exist). A raid is an **event** marked `raid: true` in `events.json` (`raid_thieves`, `raid_rustlers`, `raid_beasts`, `raid_burglars`, one per kind in `raids.json`): `GameEvents.is_eligible` never offers them while exploring, `GameRaids.on_years` begins one (never while another waits, and only a kind with something to take: thieves need gold, burglars a carried item, rustlers and beasts an animal; `GameEvents.explore` no longer overwrites one that came with the year), and the heir settles it on the event screen. The outcome effect `defend: <kind>` is trusting the guards: `GameRaids.defend` beats the raid off with `beat_off_chance` (0 with no guards, up to `beat_off_max`) or it takes what it came for (thieves a share of the gold, cut by the guards' `guarded_loss`; burglars a carried item; rustlers an animal; beasts kill one). Other choices pay, trick (a skill check, failing into `defend`) or ride out and fight (a `fight` outcome). Not built: renown and infamy changing the chance, hired guards and walls, and raiders beyond these four.
- **Farm animals.** `GameFarm` (core, no UI; `data/creatures/farm.json`, checked by `tools/check_data.gd`) is the worth of the creatures flagged `farm: true` in `creatures.json` (sheep, cattle, pigs, chickens, goats, geese and horses, with art in `data/art/creatures.json` held to the usual style). **Farm animals are never fought and never found beside the dead**: the hunt's and the events' creature pools filter `farm` out (`GameDynasty.start_hunt`, `GameEvents._in_era`/`_creature_for`, the event validator), so every seeded fight and the golden digests are unchanged. They are **bought young at a town's market** (`GameFarm.buy`, flat prices, the name and sex keyed on the seed and what is kept, a bird skipping its egg), raised and bred like any creature (they have sizes in `ranch.json` and families in `breeding_rules.json`), give **wool, milk or eggs** each year through `work_of` (the pay follows the season, `season_mult`, and how well the animal is kept, `mood_scale` from the `mood_floor` to 1: `GameFarm.yield_mult`, read by `GameRanch.yearly_work`; wild creatures' work is untouched), and can be **slaughtered** for meat and hide once, past their egg (`GameFarm.slaughter`, paid by stage and mood, ending the animal). The Creatures tab has the Market (buy buttons, shut away from a town with the reason shown) and a Slaughter button asking twice. A new farm animal needs creature data with `farm: true`, art, a size, a family, a market price and meat and hide (`GameFarm.validate`). A horse gives `haul` work (a plough and cart, not wool or milk) and is **never slaughtered**: `farm.json` `settings.no_slaughter` lists such species and `GameFarm.slaughter_value` returns 0 for them (the validator wants every farm animal either to have meat and hide or to be listed there). **Bees:** the beehive (`bee`, name Beehive, `hive: true` in `creatures.json`) is the eighth farm animal: bought as a **swarm** at a town's market (28 gold), kept like any creature (size `hive`, adult in 5 years), makes **honey** (6 gold a year, `honey` in `farm.json` `season_mult`: summer 1.5 down to winter 0.2) and is never slaughtered (`no_slaughter`). A hive **has no pairs**: it is born (so it has a roster entry and a young stage) but `GameBirth.can_breed` is false for a hive (`is_hive`), `GameBreeding.able` refuses it whatever its flag says, so two hives of opposite sexes never breed and it needs no family; `GameBirth.validate` wants a hive to be a born farm animal. (Its roster entry still carries a sex like any creature's; nothing reads it.) `tests/test_game_hive.gd` checks. Not built: the market varying by place, and trade.
- **Companions in the world.** `GameCompanions` (core, no UI, no screen yet; `data/companions/world.json`, checked by `tools/check_data.gd`) gives a hired companion (`GameParty` member) an **order**: `follow` (default, nothing saved), `stay`, `gather` or `guard`. `set_order` writes it on the member (`order`, erased for follow) and `GameParty.from_dict` loads it through `load_order` (unknown or mistyped means follow). Where companions stand is **runtime, not saved**: `agents_for(d, hx, hz)` puts one agent per member beside the heir and `reconcile` follows hires and departures. `step_all(d, agents, view, tick)` returns `{agents, events}` (inputs untouched): `view(d, hx, hz, threats, router)` is `GameBehaviour.world_view` plus the heir, threats and an optional `GamePath.router`, and movement uses `GameBehaviour._route` and `_move`. An order change resets the work and sets the post to where the agent stands. Follow keeps `follow_min`..`follow_max` (hysteresis), a ring offset by index so they do not stack, and teleports past `follow_catchup`; guard intercepts the nearest threat within `guard_radius` times the class share of the post, is clamped to that reach and sends one `alert` per sighting; gather `scan`s nodes within `gather_radius` of the post (nearest first, ties by x then z), plans a few, claims one so two companions do not share a trip, works `gather_ticks` and adds the node's material times the class share (`classes`, `default` otherwise) to `GameDynasty.stores`. `GameDynasty.gathered` (`{"x,z": world year}`, saved only when not empty, loaded clean by `load_gathered`) marks a node until `regrow_years` have passed. No dice, no combat; the autopilot never steps companions or gives orders (`tests/test_game_companions.gd` checks). Every companion class needs work shares in `classes` (the validator checks). Not built: a screen, guards that fight, loads carried and returned, other work, night watch.
- **Titles.** `GameTitles` (core, no UI) reads `data/titles/titles.json`: each title has a `kind` (`personal`, ending with the heir and kept in their lineage record, or `house`, kept by the dynasty), an `about` that says how it is earned, a `when` condition read from the dynasty's own state (`stat` with `gte`/`lte` from `GameTitles.STATS`, `boss`, `boss_by_heir`, `flag`, `trait`, `class`, `race`, `family`, and `all`/`any`/`not`) and an optional `perk` (only `persuasion`, cheaper shops, while worn; `GameItems.persuasion` adds it). Earned ids are saved only once there is one (`GameHeir.titles`, `title_worn`, `GameDynasty.house_titles`, and `titles` in a lineage record) and load cleaned of anything unknown. **Earning is asked for by the screens** (`GameApp.show_state` and the life screen's `_changed` call `GameTitles.announce`), never by the rules of a life: the autopilot and the golden scenarios earn nothing and draw no die for it, so their results do not move. A new condition kind needs its branch in `met` and `_cond_problems`; `GameTitles.validate` is part of `tools/check_data.gd`. The Chronicle's Titles tab lists earned and unearned titles and puts one on or off. `tests/test_game_titles.gd` checks all of it, including that every title can be earned.
- **Achievements.** `GameAchievements` (core, no UI; `data/achievements/achievements.json`, checked by `tools/check_data.gd`) keeps the dynasty's milestones: each is a `count` about the whole house (`COUNTS`: generations, years, ages, legends, legend_kills, heirs, house, creatures, bred, crafted, built, heirlooms, titles, gold, milestones) reaching a `goal` (or `goal_from: house_max`). Once reached it is on `GameDynasty.achievements` for good (`{id: {gen, year, heir}}`, saved only once there is one, loaded clean and in the data's order by `load_state`), even if the count later falls. A milestone may award a house title: the title's `when` is `{achievement: id}` (a test kind in `GameTitles`), and the validator wants the two to name each other. **Reaching is asked for by the screens**: `GameTitles.announce` calls `GameAchievements.announce` first, so a milestone and the title it brings are told in the same pass; `GameTitles.update` alone does not. The rules of a life never ask, so the autopilot reaches nothing and no die is drawn. The Chronicle's Milestones tab draws `describe(d, id)` (who reached it and when, or `have of goal`). A new count needs a branch in `count`, an entry in `COUNTS` and a milestone that uses it. An Age is `age_length` (1,100) generations, so Age milestones are far apart. Not built: rewards other than titles, and milestones for one heir's deeds (those are personal titles).
- **Faction reputation.** `GameFactions` (core, no UI; `data/factions/factions.json`, checked by `tools/check_data.gd`) is how six factions judge the heir by their ancestors. **A standing is worked out, never saved**: `remembered(d)` is the living heir (`ago` 0) and every dead heir `history` keeps in full (heirs folded into the Ages are forgotten); each faction's `remembers` rules (`HEIR_RULES`: class, level, battles, kills by creature or tag, gold, cause, titles; `each` per time it applies, within `cap`) weigh each of them, an ancestor's share fading by the faction's `memory` per generation, and its `house` rules (`HOUSE_RULES`: echo of glory or infamy, bosses slain, milestones) weigh what belongs to the whole house. `standing(d, id)` is -100 to 100, `rank` the highest of `ranks` it reaches (hostile, wary, neutral, trusted, honoured), `reasons` what was weighed, strongest first. At `boon_rank` or better `take(d, id)` gives the living heir the faction's gift once in their life, in a town (gold scaled as prices are, potions, XP by level; doubled at the top rank; marked in `GameHeir.boons`, saved only once there is one), and at the top rank the faction confers a personal title whose `when` is `{faction: id}` (a test kind in `GameTitles`; the validator wants the two to name each other). No dice. **Little in a life reads a standing**: the gift and the title (below) and, in the four towns, prices, hire fees and training (see the last sentences), and the autopilot takes no gift, so the golden scenarios and the fight digests do not move. The Chronicle's Factions tab draws `describe(d, id)` and calls `take`. A new rule kind needs a branch in `heir_points` or `house_points`, its name in the list and a check in `_rule_problems`. In the four towns a faction keeps (`towns` in factions.json: Kingshold the Noble Houses, Brinehaven the Thieves' Guild, Ironford the Warrior's Order, Hearthmere the Church), the heir's standing with that faction also moves the numbers there by rank (`town_effects`): shop and temple prices (`GameItems.price_mult`), companions' hire fees (`GameParty.fee`) and the XP of training (`GameDynasty.train`), through `GameFactions.town_mult(d, key)`, which is 1.0 anywhere else or with no living heir. **This is a balance change**: the autopilot visits towns, so the stored life digest `live|4` was recaptured and the harness was run before and after. **Quests and raids:** the standing with the faction that keeps a quest's `giver` town (`towns`) scales the quest's gold and XP by rank (`quest_effects`, read by `GameQuests.reward_gold` / `reward_xp`, so the board shows what is paid now; a giver no faction keeps pays as before), and the standing with the Thieves' Guild scales the chance of a raid on the house (`raid_effects`, `GameFactions.raid_mult`, read by `GameRaids.chance`). Neutral is exactly 1. **This was a balance change** (the autopilot visits towns and is raided): `live|4` in the round baseline was recaptured; the harness over seeds 1-40 went from 3.4% battle deaths (109 of 3,200 lives, range 2.8-4.1%) to 3.2% (102 of 3,200, range 2.6-3.9%), both in band (over seeds 1-12 it read 3.4% to 2.7%, which was noise). `tests/test_game_faction_effects.gd` checks. Not built: standings changing which foes attack or what hunts meet, the heir acting to win a faction over, and faction quests.
- **Dungeons.** Each of the six dungeons of `world.json` is an interior with a look, contents and loot of its own. **Looks:** `GameDungeonArt` (core, no UI; `data/world/dungeon_themes.json`, checked by `tools/check_data.gd`) gives each dungeon a theme (`warren`, `barrow`, `ember`, `temple`, `halls`, `rift`): a palette, 8 by 8 pixel glyphs for three floor looks, a wall (`wall_face` seen from the room, `wall_top`), door, exit and props, `propdefs` (solid, light radius, on a wall or not), `ambient` rules (`where`: floor, edge, corner, center, pillar, head, wall_north; `roles` of the rooms they go in) and `light` (`dark` 0 to 0.9, the heir's `radius`, a `tint`). `props(space)` places the props from a hash of the dungeon id and the tile, never a die; a solid one never cuts the floor in two (`GameDungeons.still_connected`); `darkness(space, x, z, hx, hz)` is how dark a tile is for a heir at (hx, hz) (their own light, then each prop's); `entrance_rect(place)` is the 5 by 3 tiles of the open world the entrance is drawn over, the door tile at the bottom middle. `ui/play/dungeon_view.gd` (`DungeonView`, a child of `TileView` that `set_interior` makes for a dungeon in place of the chunks: a ground layer and a layer of things over it from one atlas made from the glyphs; `refresh_cell` redraws a chest opened or a trap sprung), `ui/play/dungeon_entrance_art.gd` (`DungeonEntranceArt`: the entrance drawn from rows in the data, which `_paint_standing` draws with the buildings) and the sandbox screen's `_paint_dungeon` (the creatures, the heir, and the dark drawn tile by tile over them) only draw. **Contents:** `GameDungeons` (core; `data/world/dungeons.json`) says per dungeon and per room role who lives there (`foes`: a count and a weighted pool, a creature only in its own era, the dungeon's `fallback` otherwise; the `lair` of `world.json` is the boss in its `boss_lair` room while it is stirring), what stands there (`containers`: a kind and a loot tier), `traps` and `features` (a shrine that heals once, or an inscription, on a prop of the theme). Where things stand (`layout(space)`) is a function of the id; who is met uses dice keyed on the seed. The floor plans are in `spaces.json` `rooms` with a `role` on every room. **Acting:** `GameSandbox.enter` gives a dungeon `GameDungeons.walk_cells` (solid things are `prop` cells) and its `denizens` (GameBehaviour agents held in their room, seeing the heir only from their own room or its door); `use()` beside a container or feature is `GameDungeons.use_thing` (the loot is `GameDungeonLoot.roll`, and what was opened, sprung, used or killed is `GameDynasty.dungeon_marks`, `{"o|t|f|k:place:key": world year}`, saved only when not empty and loaded clean by `GameDungeons.load_marks`, coming back after `refill_years` or `foe_years`; a unique found is `u:item`, for good); stepping on a hidden trap costs a share of health and never kills; a denizen in `chase` that reaches the heir (`_dungeon_contact`) starts the open-world fight (`start_encounter(ids, place)` at the dungeon's `danger`; the lair's boss alone through `start_legend_at`), which draws the dynasty's dice as any sandbox fight does and nothing else here does. After it (`after_fight`, with `GameDynasty.last_result`) a win marks them killed and gives their drops (`GameDungeonLoot.roll_drop`); a flight or defeat puts them back and the heir at the way out. **Loot:** `GameDungeonLoot` (core; `data/items/dungeon_loot.json`) builds from `GameLoot`'s forms, materials, affixes and rarities (`pick_weighted`, `pick_affixes`, `materials_at` are its public handles): `roll(d, dungeon, container, tier, kind, depth, cycle)` is `{gold, items, materials, uniques}`, a pure function of the seed, dungeon, container, tier and cycle (the calendar's refill period), scaled by the generation (`tier_ceiling`, `grade_of`, gold by `enemy_scale`) and shaped by the dungeon's table (`slot_weights`, `form_bias`, `material_tag_bias`, `tier_shift`, `gold_mult`, `materials`, `drops`), the container kind and the room's depth (doors from the entrance); `give` puts it into the purse, stores and pack (what is too heavy is sold where it lies); the items are ordinary ids, so `GameItems.sell_price` and every shop work. Eight named unique items (items.json, `unique`, `shop` empty, each with a listed material and a weight: the Hollow King's crown fragment, the Warchief's Cleaver, the Emberscale Cuirass, the Tidecaller Trident, the Pearl Locket, the Stonefather's Rune Maul, the Delvers' Runeplate and the Shard of the Unmade) are found once each, in a container of a room `role`. Nothing here is asked by the rules of a life, so the autopilot and the golden digests do not move. A new dungeon needs a theme, contents, loot and a plan with roles; the validators (`GameDungeons`, `GameDungeonArt`, `DungeonEntranceArt`, `GameDungeonLoot`) check them. Tests: `test_game_dungeon_art.gd`, `test_game_dungeons.gd`, `test_game_dungeon_loot.gd`, `test_game_dungeon_walk.gd`. **The entrance is a body:** every tile of its 5 by 3 picture but the door tile is solid (`GameDungeonArt.solid`, `blocks`; read by `GamePath.world_ground`'s `block`, `GameBehaviour.world_view`'s `walkable` and `GameWalls.line_clear`'s stoppers), so the heir, companions, creatures, the building rules and A* routes go round the hill to the door tile, which is entered from the open ground below it, and a blow does not pass through it; the dungeon's anchor ground is flat and clear for 4 tiles, so the way is never walled off. `tests/test_game_dungeon_entrance.gd` checks. **Locked doors and keys:** each dungeon's `locks` (a door between two rooms by their ids, a `key` id, a name) and `keys` (an id, a name, the `room` it lies in and the container `kind` and `tier` that holds it) in `dungeons.json`. `layout` puts the key in a container on the room's edge (placed first, so no other container takes the spot; the record has `key`) and `locks` at the door's cell. `GameDungeons.walk_cells(space, d)` makes a door whose lock is not open a `locked` cell (not in `GameInterior.WALKABLE`, so it is solid to the heir, creatures and paths; drawn as the door with a padlock over it by `DungeonView`); without the dynasty every door is open, as before. `thing_near(space, x, z, d)` also finds a shut door; `use_thing` opens a key's container (the key is given once) and `use_lock` spends the key and opens the door, and the sandbox turns its cell into a `door`. The state is two kinds of `dungeon_marks`, `y:place:key` (held) and `d:place:lock` (opened), which never expire and are saved only once set. Keys are marks, not pack items, so shops, weight and selling never meet them. `GameDungeons.solvable(space)` (checked by the validator) walks a dungeon taking keys in any order and fails when a key is shut behind its own door. `tests/test_game_dungeon_locks.gd` checks. **People:** each dungeon's `people` in `dungeons.json` (two per dungeon: an id, name, `room`, `kind`, a `race`, `class` and `color` for the figure, a `greet` and what the kind needs): a `prisoner` is freed with Use for a `GameDungeonLoot.roll` of their `tier`, a `healer` eases the heir by `pct` of their health (not charged when at full health), a `hint` names the room of the next key not yet found (`hint`, `with_key`, `done` texts). `layout` stands each on a floor cell of their room away from doors (a solid cell, `person` in `walk_cells`, checked by `solvable`), `thing_near` finds them and `GameDungeons.talk` is what Use does; what a person gave is a `p:place:id` mark that comes back after `settings.people_years`. The sandbox screen draws them as `SpriteArt.hero` figures. `tests/test_game_dungeon_people.gd` checks. **Companions:** the party goes in with the heir. `GameSandbox.enter` seats the agents on the floor nearest the way in (`_seat_companions`), `_dungeon_tick` runs `_dungeon_companions` (GameCompanions' own `step_all` with `view.indoors` set and `walkable` the dungeon's cells, so a gather order only follows; their threats are the non-boss creatures of the heir's room), a guard's `engage` is `GameCompanions.duel` on its own dice (`_dungeon_guard_fights`: a win kills the creature with a `k` mark and its drops, a loss leaves the guard resting, the lair's boss is left to the heir), and `leave` puts the party beside the door. The screen draws them. `tests/test_game_dungeon_party.gd` checks. **Spells:** the heir's own spells are `GameCasting.self_cast` (see Shops: one system with the shops' spellcasting, paid in MP). On a dungeon's floor `GameSandbox.cast(id)` is the only way in (a dungeon, no battle); the sandbox screen's Cast button, shown only in a dungeon when the heir has such a spell, opens a menu from `GameCasting.self_castable`. A ward (the `trap_wards` blessing, cast by the heir or bought at a shop) turns the next hidden trap (`GameCasting.ward_up` is asked by `_dungeon_arrive`, `spend_ward` marks it used; the blessing stays for the next fight). `tests/test_game_self_cast.gd` checks. **Not built:** damage and control spells outside a fight (a fire spell lighting a brazier, a spell breaking a lock), class skills as casts, people who move, trade or have errands in dungeons, trap disarming, creatures that follow the heir out, a second floor, and the underworld.
- **Tutorial.** The first-heir tips are chosen by `GameTutorial` (core, no UI) from the dynasty's own state, using the rules and text in `data/ui/tutorial.json`; nothing of it is saved, so it works on old saves. Only whether the tips are on lives in `user://settings.cfg`. The strip (`ui/play/tutorial_tip.gd`) is one row on purpose: a phone at large text has no height to spare. A new tip needs a `when` that includes `first_generation` and text of 125 characters or fewer; `tests/test_game_tutorial.gd` checks both. The open world's tips are the steps with screen `sandbox` (move, dig, wood, build, room, orders, night; `GameTutorial.SCREENS` lists the screens): `current(d, "sandbox", ctx)` answers from dug ground, stores, `GameBuild`, the party's orders and `GameDay`, and takes in `ctx` the yes-or-no facts only the screen knows (`GameTutorial.CONTEXT`, now just `moved`; absent or mistyped is false). A new question goes in `PREDICATES` with a branch in `holds`; a new placeholder in `fill` (`{home}`, `{claim}`). No sandbox screen shows them yet.
- **Text in data.** The text the player reads is in catalogs under `data/text/`, found by key. `data/text/battle.json` (the fight's log lines) is read through `GameMessages.line(key, {placeholders})`; `data/text/life.json` (the life actions, events and their choices, party, items, houses, quests, feats, skills, plague and disease, the fight's round commands and reports, replay and save errors) is read through `GameMessages.text("life", key, {placeholders})`. Add a line as a new key and a call, never as a string in code. `tests/test_game_text_catalog.gd` renders every moved line against its old literal; `tests/test_game_data.gd` checks the battle catalog, and `tools/check_data.gd` fails on a key the code asks for that the catalog lacks, or one nothing asks for. **Still in code:** the validators' messages (developer text, never shown), English grammar (the `a`/`an` choice in `game_feats.gd`), and a few names built from parts (`GameHeir.full_name`). The modules that keep their own JSON text (`breeding_rules.json`, `factions.json`, `ages.json`, `achievements.json`, and the `text()` helpers of craft, loot, ranch, raids, farm, finding, companions, realms, titles, heirlooms, world events, hard mode, build, mine, day, subclass, report and carry) are read through those helpers, so GameLocale does not translate them yet. The screens' own text in `ui/play/` is not part of this, and the life screen still picks out journal lines by their English start (`begins_with("Level up")`), so a translation loses that highlight.
- **Localisation.** `GameLocale` (core, no UI; `data/text/locales.json`, checked by `tools/check_data.gd`) chooses the language of the text that is in data. `text(catalog, key, source_text)` returns the source line in the game's own language (`source`, English: so nothing changes for a game that never switches, and the golden digests do not move), a translation's line when the chosen locale has one **using exactly the source's `{placeholders}`** (any order), the source line otherwise, and for the **pseudo-language** a line made on the fly (`pseudo`: every letter accented from `pseudo.map`, padded by `expand`, bracketed, placeholders untouched). Catalogs are `battle` (`data/text/battle.json`, read through `GameMessages.line`), `life` (`data/text/life.json`, read through `GameMessages.text`), `tutorial` (the tips by step id, read in `GameTutorial.current`) and `talk` (the townspeople's words, `data/text/talk.json`, read through `GameTalk.text`). A translation is `data/text/locales/<id>/<catalog>.json` as `{"lines": {key: text}}`; `check(id)` lists unknown keys, wrong placeholders and missing lines, and the validator fails a listed locale that is not complete. The choice lives in `settings.cfg` (`UiSettings.locale`, set at start by `GameApp._ready`), never the save; the menu shows a Language row only when `offered()` has more than one (the pseudo-language is `hidden`, chosen by `locale="pseudo"` in the settings file). `tests/test_game_locale.gd` checks the font has `sample_chars` and the pseudo letters; `tests/test_game_mobile.gd` lays the screens out in the pseudo-language and holds the tip strip to `tip_max_height_share` of a phone screen (`data/ui/mobile.json`), because a wrapped tip is never off the screen, it eats it. **The module-owned texts listed under "Text in data" are not translatable yet**, and only English ships. A new catalog needs a branch in `source_lines` and a reader that calls `GameLocale.text`.
- **Save slots.** `GameSaves` (core, no UI) owns the slot files: slot 1 is the original `user://dynasty_save.json`, the others add `_2`, `_3` (`balance.json` "save_slots"). `GameDynasty.save_path` stays "the file in use"; `GameApp.use_slot` points it at the chosen slot, so saving and loading are unchanged. Saves are written atomically and keep the one before as `.bak`, which loading falls back to. A backup is `GLBK1:` + base64 of the gzipped save, copied to and from the clipboard (`ui/play/clipboard.gd`, which tests fake) or written to and read from a `.glsave` text file holding the same block (`GameSaves.export_file`/`import_file`; `ui/play/file_picker.gd` uses the platform's file dialog where there is one, else the Downloads or `user://exports` folder, and tests fake it); `GameSaves.import_text` checks the shape before anything is loaded. If the save format gains a required key, add it to `GameSaves.REQUIRED` only when old saves have it too. The file is written by `GameDynasty.to_save()`: `to_dict()` (the shape the golden digests use, never changed by this) at the version in `GameSaveVersion.CURRENT`, plus a fight in progress under `"battle"` (`GameBattle`/`GameRound` `to_dict` and `restore`, in Godot's exact binary encoding as base64, values only), so a game closed mid-fight reopens in the same fight and plays on as if never saved. `GameSaves` runs `GameSaveVersion.upgrade` before `from_dict`: one tested step per version; a save from a newer game is turned away. A format change needs a new version and its step.
- **Hard mode.** `GameHardMode` (core, no UI; `data/game/hard_mode.json`, checked by `tools/check_data.gd`) is three options chosen **once, at the founding** (`GameDynasty.new_game`'s last argument, `GameApp.new_game`, the title's Hard mode button and `ui/play/hard_mode_panel.gd`) and kept on the dynasty as `hard`: `{permadeath: true, ironman: true, gen_cap: n}`, a key only for an option that is on, the whole thing saved only when one is (so a plain save is the text it always was) and loaded clean by `load_state` (wrong kinds dropped). `found(d, opts)` refuses a house that already has options (none can be changed or switched off) and one that is no longer fresh (`is_fresh`: generation 1, no hunt, year 0), so none can be switched on later. **Permadeath:** `GameDynasty._die` asks `line_ends(d, cause)` (the causes in `permadeath_causes`, only "slain in battle"; old age and sickness pass the line on) and ends the saga through `GameAges.end_saga` with one more line. **Generation cap:** `last_gen(d)` is the dynasty's cap (one of `gen_caps`) or `GameAges.max_generations()`, whichever is lower; `_die`, `choose_heir`, `from_dict` and the succession screen ask it, never `max_generations` directly. **Iron-man:** `GameHardMode.after_save` (from `save_to_disk`) removes the `.bak`, `GameSaves.export_text`/`export_file` refuse the slot, `import_text` refuses a block holding an iron-man house, and `GameSaves.restore_into` (which the title now writes backups through) refuses to write over one; `peek` gives `ironman`, and the title and the menu shut their backup buttons with `why_no_export`/`why_no_restore` as text. No dice: with nothing on, every rule answers as before and the golden digests do not move. The Chronicle's Statistics list the options only when one is on. Replays record the options (see Replays). Not built: a damaged iron-man save has no `.bak` to fall back on, and nothing stops a player copying the save file by hand or editing the mark out of it.
- **Error reports.** `GameReport` (core, no UI; `data/ui/report.json`, checked by `tools/check_data.gd`) makes a report the player can pass on: `build(d, env, errors, note)` is `{format, game, save_version, env, note, errors, journal, save}` and `to_text` packs it as `GLER1:` + base64 of the gzipped JSON. **The game never sends it**; the player copies or saves it. Of `env` only the keys in `env_keys` are kept (so whatever a screen offers, nothing else about the device leaves), and the note, errors and journal are cut to the limits in `settings`. The save is `to_save()`, a fight in progress included; `d` may be null when no house could be loaded. `from_text` returns `{ok, error, report}` cleaned to the same shape and limits, and turns away (never crashes on) a block that is not a report, is damaged, is from a newer `FORMAT`, or whose save `save_problem` says cannot be played; `dynasty(report)` loads the house through `GameSaveVersion.upgrade` and `backup_text(report)` gives the save as a `GLBK1:` backup the game's own Load reads. `GameErrorLog` (core, extends Godot's `Logger`) remembers the last errors, warnings and script errors as lines (`install(keep)`, `recent()`, `clear()`, `remove()`), in memory only, guarded by a mutex because errors can come from any thread; it is installed only when the player has switched the menu's **Error log** on (`UiSettings.error_log_on`, off by default, in `settings.cfg`; `GameApp.set_error_log` installs or removes it, and `_ready` installs it for a player who asked). The menu's Problems section also has **Report a problem** (in every menu mode, the title's too), which opens `ui/play/report_panel.gd`: it shows `text.never_sent` and `text.holds`, takes a note, and copies the report (`Clipboard`) or saves it as a `.glreport` file (`FilePicker.save` with its own filter); the report is built from the house being played (none at the title), `ui/play/report_env.gd` (`ReportEnv.facts`: the only place device facts are gathered) and the log. A new fact about the device goes in `env_keys`, in `ReportEnv.facts` and in `text.holds`; `tests/test_game_report_ui.gd` fails if the screen offers a fact a report may not keep. **A bad close is noticed**: `GameSessionMark` (core, no UI) writes a mark file when a session begins (`GameApp._ready`, beside the settings file: `session_mark_path`) and removes it when the session ends properly (the window closing, the app going to the background, `_exit_tree`); a mark still there at the next start sets `GameApp.closed_badly`, and the title then shows one row saying so with Report a problem and Dismiss. The mark holds nothing but the word "running". The error log is memory only, so a report made after a crash carries the save and not that session's errors. Not built: reading a report inside the game, and keeping a crashed session's errors.
- **Family house.** `GameHouse` (core, no UI) holds the three upgrade tracks, Hall (companion places), Yard (training XP) and Ranch (pens, hatchery and nursery for the creatures, see Creature growth), bought with the heir's gold and stored on the dynasty as `house` (only once something is bought). Costs and effects are in `balance.json` (`house_*`; the Ranch's effects are in `data/creatures/ranch.json`). Use `GameParty.max_size(d)` for the party's places, never the base setting, so the Hall counts. The House button on the life screen opens `ui/play/house_panel.gd`, which only calls `GameHouse.buy` and draws the rows; a row that cannot be built is disabled, with its reason shown as text under it.
- **Heirloom upgrades.** `GameHeirlooms` (core, no UI; `data/items/heirlooms.json`, checked by `tools/check_data.gd`) lets each heir have each of the house's heirlooms (`GameDynasty.heirlooms`, `{name, boss, gen}`) reworked once in their life: `upgrade(d, index)` needs a place with the `needs_service` service (a forge) and gold (`cost`: `cost_base` times the square of the level bought, scaled by the generation as prices are), raises the heirloom's `level` (to `max_level`), and records `worked_gen` and the heir's name in `smiths`; a second rework in the same generation is refused, so an heirloom grows over generations. `GameDynasty.heirloom_bonus()` is now `GameHeirlooms.total_bonus(d)`: the count times `heirloom_bonus` **worked out exactly as before**, plus `level_bonus` per level of the first `heirloom_max` heirlooms, so a hall with no levels gives the same number to the last bit (`tests/test_round_determinism.gd` holds). The three keys are written only once an heirloom is reworked and load cleaned by `load_list`. No dice; the autopilot reworks nothing. The House panel shows an Heirlooms button only when the house holds one (`ui/play/heirloom_panel.gd`). The validator refuses settings under which a full hall would more than double an heir's power. **Effects:** each legend's heirloom also gives a small effect of its own (`effects` in `heirlooms.json`: the Fang more hunt gold, the Crown better shop prices, the Scale more hunt XP, the Heart fewer raids on the house, the Shard a little of two), grown by `effect_per_level` for each level reworked and capped at 25% fully worked (the validator checks, and that every legend's heirloom has an entry). `GameHeirlooms.effect(d, key)` adds the first `heirloom_max` and is exactly 0.0 with none; it is read by `finish_battle` (gold and XP, taken **before** the fight's own claim, so a legend's heirloom helps from the next fight and the golden fight scenarios do not move), `GameItems.persuasion` and `GameRaids.chance`. The heirloom panel names the effect. No dice. **This was a balance change** (the autopilot slays legends): the six autopilot-life digests `live|1` to `live|6` in the round baseline were recaptured, every fight scenario is unchanged; the harness over seeds 1-40 went from 3.2% battle deaths (102 of 3,200 lives, range 2.6-3.9%) to 3.2% (101 of 3,200, range 2.6-3.8%). `tests/test_game_heirloom_effects.gd` checks. Not built: heirlooms from anything but a legend, effects that need a choice (a charge to spend), and losing one.
- **Trials.** `GameTrials` (core, no UI) runs ROADMAP item 67 from `data/world/trials.json` (design in `docs/TRIALS.md`). Placement is a pure function of the world seed; a trial needs its quest steps done first (`do_step`), is run by a master creature whose lines come from data, takes world hours (`wait` feeds `GameClock`), and is checked on its own dice, never the dynasty's. Gains read through `GameTrials.bonus` (from `GameHeir.trait_total` and `GameCarry.capacity`, skipped when `trials_done` is empty). State: `GameHeir.trials_done` and `GameDynasty.trials`, saved only once set. `GameBot` must never mention a trial; `tests/test_game_trials.gd` checks it. **The screen:** the House panel's Trials button opens `ui/play/trials_panel.gd` (a modal; only calls the core and draws, no tooltips, reasons as text): `GameTrials.listing(d)` is every trial standing in an open realm as `describe` gives it (`status` way, ready, shut, active or passed, the next step and why it cannot be done, the gain as words by `gain_preview`, the chance of passing), the buttons do `do_step`, `start`, `wait_out` (the hours that are left, on the world clock), `finish`, `leave` (asks twice) and, for a trial won by a fight, `begin_master`, which hands the screen to the battle through the life screen's `_changed`. `GameDynasty.finish_battle` ends with `GameTrials.settle_master`, which does nothing at all without a trial under way, so a win over the master wins the trial and no other fight changes. `tests/test_game_trials_screen.gd` checks. **On the map:** `GameWorldMap.trial_markers` (core) gives a marker for each open-realm trial whose site is found (first step of the way in done) or passed, and the world map panel draws them; the panel's rows draw each master as its own look (`SpriteArt.master`: its creature's sprite repainted by `data/art/masters.json`, a palette and a few marks, checked by `SpriteArt.validate` and the style; the fight with a master draws it too through the foe's `master_of`; `tests/test_game_master_art.gd`). **In the sandbox:** a found open-realm trial stands at its map tile (`GameTrials.sites`/`site_near`/`site_use`; the screen draws a ring of stones and the master's look there); Use within `site_reach` makes the master speak and opens the Trials panel (`open: "trials"`), the place line names it, nothing is saved (`tests/test_game_trial_sites.gd`).
- **Family tree.** `GameFamilyTree` (core, no UI) reads the dynasty's `history`, living heir and echoes into one entry per generation: each heir's parents, spouse, children, death (cause and level), traits and the echoes from their generation. Older heirs folded into the Ages are counted only and their names are not kept, by design. The chronicle's Family Tree tab (`ui/play/chronicle_panel.gd`) draws it; it has no tooltips, so the mobile suite needs nothing more.
- **Statistics.** `GameStats` (core, no UI) works out the dynasty's numbers from `GameAges` and the kept heirs: heirs lived, generations, the current Age, the Ages reached (`ages_reached`: every Age a heir died in, plus the current one, so a new house has Age 1), deaths by cause, legends slain, the greatest heir and the gold of each kept heir. The chronicle's Statistics tab draws them. Each Age row keeps `gold_sum` and `gold_known` (the gold of its heirs at death), so the average per Age survives folding and is drawn as a list, not a plot; an Age saved before gold was kept reads as not recorded. Nothing here is saved.
- **Sex.** `GameSex` (core) gives every heir, spouse and child a sex: the founder picks it at the start, a spouse is always the opposite sex, and children are rolled from their own seeded dice (never the dynasty's main dice, so no life changes). Old saves are filled in on load (`GameDynasty._fill_sexes`). The golden digests drop the `sex` key (`Scen.drop_sex`, in place: copying would break the shared lists those digests rely on).
- **Accessibility.** Three yes-or-no options in `settings.cfg` (`UiSettings.ACCESS_KEYS`), set from the menu's Accessibility row. UI code takes colours from `Kit.good()`, `Kit.bad()` and `Kit.dim()`, never `Kit.GOOD`/`BAD`/`DIM` directly, and animations take their time from `UiSettings.motion_time()`. Colour-blind colours reach the life screen's journal lines, the state fills of the skill tree and party strip (`Kit.good_fill`, `Kit.bad_fill`, `Kit.good_muted`) High contrast reaches quiet text in the chronicle, the shop and the map, which are built as BBCode through `Kit.quiet_bb`; a new quiet line there must use it, not a literal grey. Reduced motion stops the figure moves and lunges (`FigurePose.play` and `fall`, `BattleView._lunge`), the pulse of an area cast and the hero's and foes' fades use `motion_time`, and floating numbers stay where they are and fade. Not built: sprite art keeps its own colours (a red mark in a sprite's palette is not recoloured), and nothing has been checked with colour-blind players.
- **Battle art.** The battle screen draws the hero, companions and foes from pixel sprites kept as text grids in `data/art/` (`docs/ART.md`), turned into textures by `ui/play/sprite_art.gd` (rendering only, cached). A figure is the class's 24x40 figure in the race's colours with the race's under and over layers, wearing a shirt from `data/art/shirts.json`: one picked from who they are unless the player chose one on the Looks panel (`ui/play/looks_panel.gd`, `GameDynasty.set_shirt`; saved as `shirt` only once chosen), and the heir in their gear: `data/art/gear.json` gives each weapon and armour a finish, a glow or a cape, and says per class where the weapon is and which palette keys are metal, leather, blade and wood. Art follows the style in `docs/ART_STYLE.md`, whose numbers are in `data/art/style.json` and checked by `SpriteArt.style_problems` (outline, stray pixels, colour cap, size, margins, standing on the ground; part of `SpriteArt.validate`, so `tools/check_data.gd` runs it); a new sprite must pass `tests/test_game_art_style.gd`. The textures `SpriteArt` hands out are regions of shared atlas pages (`ui/play/texture_atlas.gd`): use them as any texture, and wrap the building of a screen's many figures in `SpriteArt.begin_batch()`/`end_batch()` so the pages upload once. Anything without art keeps the old block. Each sprite figure stands in a `ui/play/figure_pose.gd` holder that breathes and plays the battle's events as moves (attack, cast, hurt, dodge, guard, fall), stilled by reduced motion. The fight is drawn in front of the land it happens in: `ui/play/scenery_art.gd` paints the place's scene from `data/art/scenery.json` (a scene per biome, place extras, weather and season layers) with its own dice seeded from the place, never the dynasty's. `tests/test_game_art.gd` checks every creature, class and race has art, `tests/test_game_gear.gd` the gear, `tests/test_game_poses.gd` the poses and `tests/test_game_scenery.gd` every place's scenery; `tools/art_sheet.gd` draws it all on one sheet.
- **Cosmetic randomness.** Anything the view randomises for show (a painted scene's scatter, particles, idle timing, camera shake) draws from `CosmeticRng` (`ui/play/cosmetic_rng.gd`: `keyed(key)` rolls the same every time, `loose()` differs each run), never from the dynasty's `rng` and never from Godot's global dice. `tests/test_game_cosmetic.gd` scans `ui/play` for both and plays fights through the battle screen to check they end exactly as the same fights with no view.
- **Gamepad and keyboard menus.** `ui/play/pad_focus.gd` (a node `GameApp` adds before the screens, `app.pad`) makes the ordinary buttons usable without a pointer. The engine moves a focus with the d-pad, stick or arrows by itself; `PadFocus` adds joypad A to `ui_accept` and B to `ui_cancel` (the engine binds neither), turns **pad mode** on at the first pad or arrow input (that first input only shows the focus), focuses the first button of the top layer (`layer()`: the open panel with a `back_close` meta, else the screen), brings back a focus that is lost when a screen is rebuilt or that strays out of the open panel, makes scroll areas follow the focus, sends `ui_cancel` (B, Escape) to `GameApp.go_back` and Start to the menu. A click or a touch turns pad mode off and drops the focus, so the ring (`Kit.focus_ring`, on every `Kit.button`) is never seen with a mouse or a finger and the stored screenshots do not change. A screen's own `_unhandled_input` for `ui_cancel` (the battle's) still comes first. Not built: aiming at a foe or an ally in a fight (those are tapped figures, not buttons), button prompts, and remapping.
- **Graphics settings.** `ui/play/graphics_settings.gd` (rendering side; `data/ui/graphics.json`, checked by `tools/check_data.gd`) holds the quality presets (`low`, `medium`, `high`: `pixel_scale`, `effects` as off, some or all, and `fps_cap`, 0 meaning uncapped) and the **battery saver**, which lies over whichever preset is chosen (its frame cap unless the preset's is lower, effects off, the engine's low-processor mode). The choice is in `settings.cfg` (`graphics`, `battery_saver`), never the save; an unknown stored preset falls back to the device's default (High on a computer, Medium on a phone). `current()` is what is in force, `effect_on(name)` asks whether an effect listed in `effect_levels` is drawn, and `apply()` (called at start and by `GameApp.set_graphics`/`set_battery_saver` from the menu's Graphics rows) sets `Engine.max_fps`, `OS.low_processor_usage_mode` and `SceneryArt.particles_on`, forgetting the painted scenes when that changes. With the particles off `SceneryArt` still rolls their dice (`Canvas.mute`), so the rest of a scene is pixel-for-pixel the same. A new effect gets a name in `effect_levels` and asks `effect_on` where it is drawn. `pixel_scale` has no reader until the 3D renderer exists.
- **Sound.** `ui/play/sound.gd` (view side, a node `GameApp` adds once as `app.sound`; `data/ui/sound.json`, checked by `tools/check_data.gd`) makes every sound from data: **there are no audio files**. A cue or track is a `wave` (sine, triangle, square, saw, noise), `notes` (MIDI numbers, 0 a rest, a list a chord), `step`, `attack`, `release`, `volume` and an optional `slide`; `samples(def, rate)` (pure, static; noise rolls `CosmeticRng.keyed`) builds it, `stream(name)` turns it into an `AudioStreamWAV` the first time it is wanted and keeps it (tracks loop, and every note ends in silence so the loop does not click). **What plays:** the battle screen's `_play_one` hands each event to `app.sound.event`, and `cue_for(ev)` reads the `events` table (a battle event type from `battle_events.json` to a cue, with `variants` on a field such as `crit` or `side`; an unlisted event is silent); `_show_result` plays `results` (victory, defeat); `GameApp._sound_state` (from `show_state`) plays the `stings` once per death (`succession`) and at the saga's end (`ended`), and asks for the music of `track_for(dynasty)`: the title's, a fight's, silence for an ended saga, else the track `ages` lists for `age_number()`, going round again after the last. **Settings** are in `settings.cfg`, never the save: `sound` and `music` (on unless the file says off) and `sound_volume`, `music_volume` (a step of `levels`, the default when unknown); the menu's Sound effects and Music rows offer Off and the steps (`GameApp.set_sound`, `Sound.choose`). Nothing in `core/game` knows of it and it draws none of the dynasty's dice, so a fight plays the same heard or not (`tests/test_game_sound.gd` compares). With no audio device (the engine's Dummy driver: headless, the screenshot tool) the streams are built but the players are never started (`has_output`); tests read `cue_log` and `music_log`. A new cue or track is data and must be played by something (the validator refuses an unused one and caps the seconds built); a new battle event is silent until it is in `events`. Not built: recorded music or samples, crossfades, sounds for buttons and life actions, and nobody has listened to it on a real device yet, so the notes and volumes are a first guess.
- **The open world as it runs.** `GameSandbox` (core, no UI; numbers and text in `data/world/sandbox.json`; tests `tests/test_game_sandbox*.gd`) is what `ui/play/sandbox_screen.gd` drives. `start(d)` puts the heir at their place's door (or where they last stood, below), keeps creatures spawned round them from `GameSpawn.spawn_at` within `radius` and lets go of those beyond `radius + keep`, and has the hired companions as `GameCompanions` agents. The heir acts by `move`, `set_route`/`walk_one` (`GamePath`, a walker), `dig` (`GameMine`), `build`/`remove_at`/`build_check` (`GameBuild`) and `order`/`cycle_order` (`GameCompanions`); `step(n)` runs the creatures (`GameBehaviour`) and then the companions, one tick per `tick_seconds`. The creatures and companions are runtime only and no die of the dynasty's is drawn; the screen feeds `GameClock` while it is open, so years pass in the open world. **The heir's position** is `GameDynasty.sandbox_at` (`{x, z, gen, place}`), written by `remember()` (the screen on every save and on leaving), saved only once set and loaded clean by `GameSandbox.load_at` (wrong kinds, non-finite numbers and tiles outside the world load as nothing); `start` uses it only for the same generation at the same place of the text game and on a tile the heir can stand on, else the door. Not built: a creature reaching the heir does nothing yet.
- **Input for a world.** `ui/play/world_input.gd` (input side; `data/ui/input.json`, checked by `tools/check_data.gd`) holds the open world's actions (`world_move_*`, `world_cam_*`, `world_zoom_in/out`, `world_dig`, `world_build`, `world_interact`, `world_cancel`, `world_menu`, `world_pan`) and their bindings: keys by Godot's names, mouse buttons, gamepad buttons and `[axis, -1 or 1]` gamepad axes. `install()` (called by `GameApp._ready`) puts them in the engine's input map under those names, so a sandbox screen asks for an action and never a key; the engine's `ui_*` actions are untouched. The validator wants every action reachable from the keyboard or mouse and from a gamepad (`pointer_only` excepted), no binding on two actions, and names the engine knows. The arithmetic is pure and static: `stick` (radial dead zone), `move_vector` (a diagonal no faster), `touch_stick`, `is_tap`, `zoom_after`, `pinch_zoom`, `facing` (one of eight `FACINGS`), `cell_ahead` (what a gamepad or keyboard acts on) and `camera_follow_seconds` (0 with reduced motion). `read()` gives `{move, look, zoom, dig, build, interact, cancel, menu}` from the input map. Touch has no bindings: the screen that tracks fingers calls the arithmetic. **Remapping:** the player's own keys are `{action: [key names]}` in `settings.cfg` (`keys`, never the save). `WorldInput.keys_of` is the player's keys or the data's, `events_for` and `install` read it, `remap(action, slot, key)` refuses an unknown action or key, a reserved key (`reserved_keys`, Escape) and another action's key (naming it), holds an action to `max_keys`, saves and re-installs at once, and `reset`/`reset_all` give the data's back; `clean_overrides` makes a damaged file safe (unknown actions and keys, clashes with what an untouched action keeps, too many, none). The menu's Controls button opens `ui/play/controls_panel.gd` (Change waits for a key, Escape cancels). Only keys are remapped: the gamepad's buttons are fixed. `tests/test_game_remap.gd` checks. Nothing reads any of this yet: there is no sandbox screen, and pointing at a tile with a mouse or finger needs the renderer's projection, which is not chosen.
- **Starting in the 2D world.** The app is one program: the life screen (text and buttons) is the hub and the 2D open world is the sandbox screen behind its "Walk the world" button (Back returns). `UiSettings.open_world_first()` (`start_in` in `settings.cfg`, never the save; the menu's **Start in** row: Open world or Life screen; on unless the player chose the life screen) makes the title's New game and Continue open the map at once: `GameApp.new_game(..., open_world)` and `continue_game(open_world)` take a flag the title passes, and `_open_world_first()` honours it only for a house in its life (not mid-fight, between heirs or at the saga's end, which come first). Calls that do not ask (the tests, the screenshot tool, the autopilot) still land on the life screen. **Launch:** the real game's entry point (`main.gd`) sets `GameApp.boot_in_world`, and then `_ready` skips the title and calls `continue_game(true)` when Start in is the open world, a house is saved (`GameSaves.newest() > 0`, the slot played last) and the last session ended properly (after a bad close the title comes first, with the error report offer); a house that cannot be read falls back to the title. An app made by a test or tool never sets the flag, so it opens the title as ever. A new dynasty, the save slots and the backups are reached from the life screen's Menu, Title screen. `tests/test_game_start_world.gd` checks.
- **Touch.** `ui/play/touch_hint.gd` gives long-press previews on phones (`TouchHint.on_hover`). `ui/play/ui_settings.gd` stores the text size, the touch layout and the autopilot cooldowns in `user://settings.cfg`, not in the save. Touch targets are at least `touch_target_px` tall.

## Conventions

- Old saves must keep loading. Missing keys fall back to defaults, and corrupt values must not crash loading, so check the type (for example `typeof(v) == TYPE_BOOL`) before using a saved value.
- A change that alters autopilot or auto-battle results is a balance change. Say so in the PR and show the before and after numbers.
- Commit the `.uid` file Godot generates beside each new script, so script references stay stable. Never commit anything under `.godot/`.
- Documentation: `docs/GDD.md` is the design, `docs/ROADMAP.md` lists what is done and what is next, and `docs/MOBILE.md` covers touch, text size and the Android and iOS export setup, `docs/BALANCE.md` covers the balance harness, `docs/ART.md` covers the battle sprites and their format, `docs/ART_STYLE.md` how new art should look, and `docs/RELEASING.md` covers publishing the APK and the Windows exe through GitHub. `TESTING.md` describes how the game's headless suites run. The `GutTest` files among the older prototype tests need an addon that isn't in this repo.
