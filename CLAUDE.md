# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Godot 4.7 with GDScript. Commands assume `godot` is on the PATH.

- Import assets and scripts (once in a fresh checkout): `godot --headless --path . --import`
- Play the game: `godot --path .` (main scene `ui/main.tscn` loads `main.gd`, which starts `ui/play/game_app.gd`)
- Run one test suite: `godot --headless --path . -s res://tests/test_game_round.gd`
  - Exit code 0 means pass. A suite prints `N checks, M failures` (or `ALL PASS`) and exits 1 on any failure.
- Run every game suite, one after another:
  `for t in tests/test_game_*.gd tests/test_round_determinism.gd; do godot --headless --path . -s res://$t || echo "FAILED $t"; done`
- Never run suites in parallel on one machine. They share the `user://` save files and fail when they overlap.
- CI (`.github/workflows/tests.yml`) runs the same suites on every pull request, one job per suite. It also fails a suite that prints `SCRIPT ERROR` even when the exit code is 0. Look for that text when you run suites by hand.
- Debug Android APK: `godot --headless --path . --export-debug "Android" build/GenerationalLegacy-debug.apk` (the Android SDK and JDK are configured in Godot's editor settings). The iOS preset only exports on a Mac with Xcode.
- Desktop builds: `godot --headless --path . --export-release "Linux" build/linux/GenerationalLegacy.x86_64` and `--export-release "macOS" build/macos/GenerationalLegacy.zip` (and `"Windows Desktop"`), each needing its export template installed (`.github/actions/setup-godot/action.yml` lists them). The macOS zip is ad-hoc signed and builds on Linux. `.github/workflows/release.yml` builds all of them on a release and on any pull request that touches it, the setup action or `export_presets.cfg`; `docs/RELEASING.md` says how to run each.
- Check all the data at once: `godot --headless --path . -s res://tools/check_data.gd`. It parses every JSON file under `data/`, runs every system's `validate()`, and checks the text catalog; it prints the problems and exits 1 if there are any. `tests/test_game_data.gd` runs it, so CI does too. A new `validate()` goes into `tools/check_data.gd`.
- Replays: `godot --headless --path . -s res://tools/replay.gd -- record SEED CLASS RACE COMMANDS [FILE]` has the autopilot live a run and prints (or writes) its replay block; `-- play FILE` plays one and exits 1, saying where, if it no longer holds on this version of the game.
- Error reports: `godot --headless --path . -s res://tools/report.gd -- read FILE [OUT.glsave]` says what a player's report holds, checks its save loads, and with OUT writes that save as a house backup to load in the game; `-- make SEED COMMANDS [FILE]` makes one from an autopilot run. It exits 1, saying why, on a file that is not a readable report.
- Long run: `godot --headless --path . -s res://tools/long_run_check.gd -- [seeds=1-2] [gens=60] [races=human,elf] [check]` has the autopilot play whole dynasties for many generations and holds each to the budgets in `data/game/budgets.json` (save size, load time, time per generation, journal size, the line carrying on). `.github/workflows/long-runs.yml` runs it every night, one race per job, and can be started by hand. A change that makes saves, loading or generations much heavier shows up there; raise a budget only on purpose, in the same change.
- Screenshots: `xvfb-run -a -s "-screen 0 1280x720x24" godot --path . --rendering-driver opengl3 --audio-driver Dummy -s res://tools/screenshots.gd -- mode=check` draws the key screens with the real renderer on a virtual display and compares them with `tests/screenshots`; `mode=update` makes the stored images again. `.github/workflows/screenshots.yml` runs the check on every pull request and keeps what it drew as an artifact. A change that moves a screen or the art must update the stored images in the same change (tick "update" when starting the workflow by hand on the branch, or run `mode=update` locally); the diff of the PNGs is what the reviewer looks at. `mode=store` draws the store page's pictures instead (`STORE_SHOTS`: six screens at 1920x1080 and the phone layout at 2532x1170) into `build/store`; it needs a display at least that big (`-screen 0 2600x1200x24`) and compares nothing.
- Rendering trial (throwaway, roadmap item 36): `godot --path . res://trial/iso_trial.tscn` runs it on a computer; the "Rendering trial APK" workflow builds it as its own Android app, and `tools/trial_adb.sh` records battery and temperature while it runs on a phone. It is left out of the game's builds. `docs/RENDER_TRIAL.md` has the method, what counts as a pass and the results table; nothing has been measured on a phone yet.
- Balance harness: `godot --headless --path . -s res://tools/balance_harness.gd` (the autopilot plays 12 seeds x 8 races x 10 generations, in parallel processes, about 4 minutes on 4 processors). Battle deaths should stay in the 3-7% band. Run it on the commit before a balance change and on the change with the same arguments; `docs/BALANCE.md` explains how to read the figures, which are noisy per seed.

## Architecture

Only the text game is wired into the app. The older prototype code is described at the end of this section.

- **Logic and rendering are separate.** `core/game/` makes no UI calls. `ui/play/` screens read dynasty state and call its methods, and they never compute results. New rules go in `core/game/` with a test in `tests/`.
- **Content is data.** `GameData` (`core/game/game_data.gd`) loads every JSON file under `data/` once, through `load_all()`. The tunable settings are in `data/game/balance.json` (Hard hunt rules, death chance), `data/combat/rounds.json` (party rounds), `data/classes/classes.json` (class skills, auto-battle `style`, openers) and `data/ui/mobile.json` (touch and layout sizes). Don't hardcode numbers in code.
- **State lives in `GameDynasty`** (`core/game/game_dynasty.gd`): the heir, the party, the world, the current battle, `command_round` and `auto_party`. It saves through `to_dict()` and `from_dict()`. A new field must load from an old save, and needs a test for that.
- **Battles.** `GameBattle` owns the round: heir, allies, foes, events and log. Its `round_on` hold lets manual party rounds use the same methods, and it is inert when no party round is open. `GameTactics.auto_turn` picks actions for auto-battle, the autopilot and any party member on Auto. `GameRound` queues manual party commands, resolves them together and retargets members who have died. A member's standing cover (`GameRound.set_cover`) is passed to the foe phase as `GameBattle.round_covers`; `_cover_for` redirects one blow a round aimed at a member below `cover_below`, drawing no dice, so a fight with no cover set plays exactly as before. With `GameRound.ask_reactions` on (only the battle screen sets it; tests, the golden scenarios and the autopilots leave it off), a foe about to strike a member below `cover_below` stops the round: `GameBattle.reaction` holds the blow, the foe phase waits in `_foe_queue`/`_foe_step`, and `GameRound.answer` strikes it and plays on. Letting it land draws no extra dice, so it plays exactly as a round that never asked.
- **Battle events.** The typed events a fight puts in `GameBattle.events` (and `GameRound` adds its round, act and foes markers to) are listed with their fields in `data/game/battle_events.json`; `GameEventSpec.problems` checks one against it. A new event, or a new field on one, goes on the list in the same change: `tests/test_game_event_list.gd` fails on an unlisted type or field and on a source type missing from the list. Life actions return text lines and emit no typed events.
- **Autopilot.** `GameBot` (`step`, `live_life`, `wants_hard_hunt`) plays without input for the tests and the "Auto" buttons. Changing when it or the battle draws a random number changes every seeded fight, and the determinism tests will catch that.
- **Determinism.** All randomness comes from the dynasty's seeded RNG. The same seed with the same commands gives the same result, including after a save and load between rounds. `tests/fixtures/round_baseline.json` is a golden file made by `tests/capture_round_baseline.gd`. Regenerate it only from the commit before a deliberate behaviour change, never to make a failing test pass.
- **World clock.** All passing of time goes through `GameDynasty.pass_time(years)` (ageing, party wages, disease, weather, the death roll, the Ages). Actions reach it with whole years; `GameClock.feed(d, seconds)` (core, no UI) is how a real-time world reaches it: seconds add up to `clock_span_years` spans (`balance.json` "clock_*"), the rest is carried in `GameDynasty.clock_carry` (saved only when above 0), and the clock holds still during a fight, a waiting event or a succession. A new per-year rule belongs inside `_pass_years`, never beside it, so both ways of passing time run it.
- **Replays.** `GameReplay` (core, no UI) records a run as its founding (seed, name, class, bloodline, race, sex) plus the commands given, with a fingerprint of the dynasty (as `to_save()` would write it, and the dice) every `check_every` commands and at the end, and plays it back to prove it. As text it is `GLRP1:` + base64 of the gzipped JSON, one line to paste. A command is `{op, ...}` from `GameReplay.OPS`; each is checked against the game's rules before it runs, so a damaged or hand-made replay is refused with a reason and never crashes. A new way for the player to change the game needs an op here (or it cannot be replayed). The recorder is used by the autopilot (`bot_on`) and the tests; the screens do not record yet. Changing what a command does changes what an old replay plays: that is a version change, and `GameReplay.play` says at which command the run first goes differently.
- **Creature birth.** `GameBirth` (core, no UI, pure functions of data) answers how creatures are born: each creature in `data/creatures/creatures.json` has `born` (`egg`, `live`, or `none` for what is not born and never bred: the undead, constructs, fiends, people-like foes) and, if born, `young` (the name of its young). `GameBirth.mode(mother, father)` says how a pairing's young are born: `kind` is `pure` (one species), `hybrid` (a recipe in `data/creatures/breeding.json` `recipes`, which says for itself how it is born) or `cross` (any other pairing of kin, which follows `settings.mixed_birth_rule`: `mother` by default, or `father`, `egg`, `live`); `young_of` names the young for the parent whose way they follow. The caller says which parent is the mother. A new creature needs `born` (and `young` if born); `GameBirth.validate` is part of `tools/check_data.gd`. Nothing here draws a die or touches the dynasty's state. `tests/test_game_birth.gd` tries all four rules and every pairing.
- **Finding young.** `GameFinding` (core, no UI) rolls whether a dead foe left an egg or young beside it, and `GameRoster` holds what the family keeps (`roster` on the dynasty, saved only when not empty, cleaned on load). The roll uses its own seeded dice (dynasty seed, hunt count, place), never the dynasty's, and the screens call `GameFinding.search_dead` in place of `GamePlague.search` (the battle result and the loot panel); the rules of a life never ask, so autopilot results and the golden digests do not move. Chances, rarity, class and trait bonuses (Wild Instincts, faetouched), the roster cap and the text are in `data/creatures/finding.json`, checked by `tools/check_data.gd`. Two more ways to find young: an event outcome can carry `find: {species: [...]}` (an effect key, validated: born creatures that are not legends; `GameFinding.take` picks one on dice keyed on the seed, generation and event), and the two nest and den events that use it **require the flag `found_young`** (set by the first creature the house takes in), so a house that has never found young is never offered them and the autopilot, which never does, sees an unchanged event pool; and a slain legend that is born may leave its young beside it (`GameFinding.after_battle`, asked by the battle screen's result, once per legend by the flag `legend_clutch_<id>`, `places.legend` times the base chance). The Beast Tamer job has no effect yet: there is no job mechanic (roadmap 60). The Chronicle's Creatures tab (`ui/play/chronicle_panel.gd`, text from `GameRoster.describe`) lists what is kept, with Sell and Set free (see Creature growth).
- **Creature growth.** `GameRanch` (core, no UI) ages the roster as the world clock passes: `GameDynasty._pass_years` calls `GameRanch.on_years`, so every way of passing time runs it. A creature is an egg (egg-layers only), young, adult, elder, then dies of old age; the lengths come from its size class in `data/creatures/ranch.json` (`size_of`, `sizes`), and the stage always follows `age` (saved with `mood`, and re-derived on load). Keeping costs gold a year from the heir (an egg half); an unpaid year sinks `mood`, and at 0 an egg spoils and a creature wanders off. **No dice are drawn** (an elder's end is stretched by a value from the dynasty seed and its id), and with an empty roster `on_years` returns at once, so autopilot results and the golden digests do not move. **The Ranch** is the house's third track (`GameHouse.RANCH`, bought like the others): the `ranch.levels` table in `ranch.json` gives each level its pens (added to `GameRoster.cap(d)`, which is the family's own places plus the pens, so never use the base `roster_cap` alone), a hatchery (eggs cost less to keep and sour slowly) and a nursery (the young the same); `GameRanch.ranch_factor` applies them and level 0 is exactly the old behaviour. A creature can be sold (`GameRanch.sell`, for its size's `value` by stage and mood) or set free (`release`); the Creatures tab asks twice before either. **Work:** grown creatures (an elder at half, none while unhappy, `work.min_mood`) do the work `work_of` gives their species: wool, eggs and venom pay gold each year (paid first, so a working ranch keeps itself), and guards turn away a share of the gold an event would take (`GameRanch.guard_cut`, applied in `GameEvents._apply`, 20% each up to 60%, and exactly nothing with no guards). The species mapping is a stand-in until farm animals exist (roadmap 62). Not built: farm animals (62), moods beyond keep, and party beasts. Raids are below. A new born creature needs a `size_of` entry and every size a `value` (`GameRanch.validate` checks).
- **Breeding.** `GameBreeding` (core, no UI; rules in `data/creatures/breeding_rules.json`, checked by `tools/check_data.gd`) runs from the end of `GameRanch.on_years`, so every way of passing time reaches it. A creature the player sets to breed (`breeding` on its roster entry; adult only) pairs with the first able creature of the opposite sex it is **compatible** with: the same species (`pure`), a species of its own family in `families` (a `cross`, which carries both parents' species in `lines`, is less fertile and likelier sterile) or a pair `GameBirth.recipe_for` knows (`hybrid`; the recipe's optional `species` is what is born; none ship yet, they need creature data and art). Each whole year the world clock crosses, each pair rolls on dice keyed on the dynasty seed, the year and the two ids, **never the dynasty's**: nothing in a life moves, and a ranch that breeds nothing does nothing. How the young are born is `GameBirth.mode` (the cross-breed rule); young keep the mother's species and `line`, inherit traits from either parent (`trait_pass_chance`, at most `max_traits`) and can mutate one; the mother rests (`cooldown`). Traits (`hardy`, `sickly`, `fierce`, `prized`, `industrious`, `fruitful`) change keep, price, work, guarding and fertility through `GameBreeding.trait_mult`. Roster entries gained `traits`, `breeding`, `cooldown`, `sterile`, and for bred young `bred`, `parents`, `line`, `lines`; all load cleaned (`GameRoster.load_list`). Not built: choosing pairs, hybrid species and their art, naming lines, and young going out with the party.
- **Creatures of the realms.** `GameRealms` (core, no UI; `data/creatures/realms.json`, checked by `tools/check_data.gd`) gives every creature a realm: `of` lists the creatures that are not of the home realm (`settings.home`, the Material Realm; unlisted means home), so `creatures.json` and the fights are untouched. **What is live:** a creature of another realm sells for `foreign_value_mult` at home (through `GameBreeding.trait_mult`, which now ends with `GameRealms.mult(e, key)`; `GameRanch.yearly_keep` asks it too). **What is written but switched off** (`settings.linked` is false until gates join the worlds): `move(d, id, realm)` takes a kept creature to a realm (`in_realm`), where it is unsettled (`unsettled`: dearer keep, faster souring, less work and young) until it has lived there the realm's `adapt_years` (`adapt`, then `settled`), unless the realm is its own; home never needs adapting to. `cross(mother, father)` says what young of two realms carry (`realms`, the mother's first, and `marks`: the mark of each world, then the parents' own, at most `max_marks`), and `on_birth` (called from `GameBreeding._birth`) writes it only when linked. A mark multiplies the same numbers a trait does (`MULT_KEYS`); the mark of an unstable realm (the Void, the Dreaming) is awake or `dormant` by the year (`awake_in`: dice keyed on the seed, year, creature and mark, never the dynasty's). `on_years` (called at the end of `GameRanch.on_years`) adapts and flickers, and returns at once for a roster with no `in_realm` and no `marks`. The new roster keys are saved only when they say something and load cleaned by `load_entry` (from `GameRoster.load_list`). Tests that change the data restore `GameRealms._cache`. A new creature of another realm goes in `of`; a new realm needs a mark of its own. Not built: creatures for the Verdant Court (none exist yet), the gates, a screen that shows a creature's realm, a pen that lives by its realm's flow of time, and cross-realm pairs outside the breeding families.
- **Subclasses.** `GameSubclass` (core, no UI; `data/subclasses/subclasses.json`, checked by `tools/check_data.gd`) is a calling layered on the heir's class: none or one (`GameHeir.subclass`, saved with `subclass_founded` only when there is one, an unknown id loading as none), never replacing the class's skills. It is **picked at the founding** (`GameDynasty.new_game`'s last argument, the title screen's pick, `GameApp.new_game`), **taken later** by the living heir for gold (`GameSubclass.take`; the price scales with the generation, a change costs double), or **passed to a child** (`GameSubclass.on_succession`, called from `choose_heir`, 50%, on dice keyed on the seed and the child, never the dynasty's). One chosen at the founding or inherited is *founded* and its perks are stronger (`founder_scale`); one taken later is at plain strength. A perk is a multiplier on a number the rules already have, read through `GameSubclass.perk(heir, key)` (1.0 with no subclass, so nothing moves without one): `find_mult` (GameFinding.chance), `keep_mult` (GameRanch.yearly_keep), `fertility_mult` and `mutation_mult` (GameBreeding), `value_mult` (GameRanch.sell_price, which now takes the dynasty). A new perk is a key in `perks` plus a place that reads it. The Chronicle's Subclass tab takes one; the life screen names it after the class. Only the Breeder exists; advanced subclasses of it and a full class born to it are not built, and replays do not record the founding subclass yet.
- **Item and material list.** `GameMaterials` (core, no UI; `data/items/materials.json`, checked by `tools/check_data.gd`) is the one list of materials (id, name, tier, tags, `weight_mult`, `price_mult`). Every item in `data/items/items.json` names a `material` and a `weight`; its tags are the material's plus its slot or kind and any `tags` of its own (`GameItems.tags_of`, `has_tag`, `material_of`, `weight_of`). A new item needs a listed material and a weight (the validator checks, and that gear does not stack and consumables do); a new material needs a tier, tags from the list at the top of the file and use by an item. Harvesting, mining, crafting and the loot generator are meant to extend this list, not make another.
- **Creature behaviour.** `GameBehaviour` (core, no UI, no screen yet; `data/creatures/behaviour.json`, checked by `tools/check_data.gd`) is how creatures act in the open world, **by tag, not by code**. Each creature lists tags (`creatures`); each tag `set`s some of the `defaults` parameters; the global `order` decides which tag wins when two set one, so the order a creature lists its tags does not matter (`params` caches, so tests that change the data must clear `_params`); `pack` is never listed, it comes from `swarm` in `creatures.json` (`is_pack`). `step_all(agents, view, seed_value, tick)` is the one state machine and returns new agents (inputs untouched): `view` is `{targets: [{x, z}], night, walkable: Callable(x, z)}` (`world_view(d, targets, night)` builds one from `GameWorldGen`: ground creatures keep off water, fliers do not). An agent (`new_agent(uid, id, x, z, hp)`) has a mode (`MODES`: idle, wander, chase, flee, return, herd, dead), a home and a heading. Rules: chase needs `hostile` and a target within `sight` (times `sight_night` or `sight_day`; keeps a target out to `lose_sight_mult` times that); `leash` (from home) ends a chase and sends it home until within half the leash; `guard_radius` makes it fight only targets within that of home; flee when hurt below `flee_hp` or `skittish`, until `flee_dist` away; an ambusher (`ambush_range`) stirs only for a close target and bursts at `ambush_speed_mult` for `ambush_ticks`; a pack animal that sees a target alerts its kind within `alert_radius` and the pack takes bearings `flank_spread` apart round the target; herds keep within `herd_radius` of their centre. Every die is `_u(seed, uid, tick, tag)` (a hash of strings, never the dynasty's `rng`). A new creature needs a `creatures` entry (the validator checks every creature has one, every wild one is hostile, every tag is used, and that a guard post is not wider than the leash); a new behaviour is a new parameter in `defaults`, a tag that sets it, and a branch in `_act` with a test. `night` is a flag the caller gives (`GameDay.is_night`, item 51, is the open world's). Not built: a tick loop that spawns and despawns, combat in the open world, pathfinding round obstacles (item 49).
- **Pathfinding.** `GamePath` (core, no UI, no screen yet; `data/world/pathing.json`, checked by `tools/check_data.gd`) is A* over 3D cells: the surface at layer y = -1 (one cell per `GameWorldGen` tile, via `world_ground(d, built)`) and dug cells at y >= 0 from `GameMine`. A `ground` is `{surface: Callable(x,z)->{h,water,biome,block}, dug: Callable, built, max_depth}`, so tests build small grids. Movers (`walker`, `climber`, `swimmer`, `flier`) set climb, drop, water and block rules; terrain, slope, diagonal and `up_mult` costs are data; diagonals never cut corners. `built` is an overlay `{"x,y,z": kind}` (wall solid; floor, road, door walkable; a floor over water is a bridge), by default the dynasty's own `built` (item 50; pass one to `world_ground` to replace it). `find` returns `{found, path, cost, expanded, partial}` and, when bounded by `max_nodes`, the way to the nearest cell reached. The heuristic uses the ground's cheapest step (`_floor_cost`), so it stays exact; `tests/test_game_path.gd` compares with Dijkstra. `GamePath.router(ground, mover)` is a Callable put in `GameBehaviour`'s `view["router"]`: chase, return and herd steer for the next cell instead of the goal; no router means item 48's behaviour exactly. Pure: no dice, nothing saved. Not built: a screen, path caching.
- **Building.** `GameBuild` (core, no UI, no screen yet; `data/world/building.json`, checked by `tools/check_data.gd`) is where and what the family may build. The family house is the first base: `claim_radius(d)` is `base_radius` round `base_place` (a town anchor) plus `radius_per_house_level` for every level of every `GameHouse` track, and nothing is built outside it. A piece is one of the four kinds `GamePath` walks (`wall`, `floor`, `road`, `door`; the validator wants both lists to match) with a `cost` in stores materials, `gold`, `refund`, `max_slope`, `over_water` and `needs_frame`. `check(d, kind, x, y, z)` returns why not or "" and `place`/`remove` return `{ok, text}`: one piece per cell, not on a `block` tile (tree, outcrop), slope to a dry 4-neighbour within `max_slope`, over water only an `over_water` piece that `_bridge_ok` joins to shore within `max_span` tiles through built pieces, a door needs walls on two opposite sides (`_framed`), underground only a `GameMine.is_dug` cell, y from -1 (surface) to the mining `max_depth`. `remove` refuses a wall a door hangs on and a plank another rests on. `rooms(d)` fills four-way over the surface from the built pieces' bounding box: closed regions (not touching the box, no open water, at most `max_room_area`) with `area`, `doors` and `sealed`. `GameDynasty.built` is `{"x,y,z": kind}`, saved only when not empty and loaded clean by `GameBuild.load_state` (bad keys, unknown kinds, out-of-world cells dropped); `GamePath.world_ground(d)` uses it. All text is in `building.json`. Pure: no dice; the autopilot builds nothing (`tests/test_game_build.gd` checks). Tests that change the data reset `GameBuild._cache`. Not built: a screen, storeys and roofs, what a room does, damage, raids that look at what is built.
- **Spawn tables.** `GameSpawn` (core, no UI; `data/creatures/spawn.json`, checked by `tools/check_data.gd`) says which creatures appear where and when. **`hunt_pool(era, place_biomes)` is the pool a text-game hunt draws from**, moved out of `GameDynasty.start_hunt` unchanged (creatures of the era whose biomes meet the place's, fallbacks included, **in `GameData.creatures` order, because the hunt picks by index with the dynasty's dice**): changing what it returns, or its order, changes every seeded fight (a balance change); `tests/test_game_spawn.gd` compares it with a copy of the old code. The rest is for the world and draws no dice of the dynasty's: `table(context)` (context from `GameSpawn.context(surface, depth, era, season, weather, night, place)`) gives `[{id, weight}]` sorted by id for a surface biome, an underground depth, or an authored place (the place's own `hunt_pool`); `weight_of` is the creature's weight times its `seasons`, `weather` and `night` multipliers; `pick` chooses by weight from the caller's dice; `context_at(d, x, y, z, night)` builds the context for a tile of `GameWorldGen` (y is -1 on the surface, else the depth: open water, a town's ground and the soil above the stone have none) and `spawn_at` rolls a creature on dice keyed on the seed, tile and slot. Each creature's `surface` biomes must be surfaces of its own `biomes` (via `worldgen.json` `surface_of`) and its `depth` band needs an underground biome (the validator checks, and that every wild creature has an entry and lives somewhere); a new wild creature needs an entry here. `night` is a flag the caller passes (`GameDay.spawn_context` passes the open world's). Hunts do not use the weights yet. Not built: hunts using season, weather and night, packs and elites in the world, caps and despawn.
- **World generation.** `GameWorldGen` (core, no UI, no screen yet; `data/world/worldgen.json`, checked by `tools/check_data.gd`) is the sandbox's surface as a pure function of `seed_value` and a tile, so it saves nothing and draws no dice. The **authored map is the skeleton**: each place in `data/world/world.json` is an **anchor** (`GameWorldGen.anchors()`, at x and y times `scale`, in the biome `surface_of` gives its first mappable biome), and the generator never moves or contradicts one: the border warp in `blend` fades to nothing at an anchor (`anchor_lock`), and towns and dungeons are flat, dry and node-free inside `anchor_radius` (`in_anchor_ground`, `height_at`). Between anchors `blend` gives the biome (nearest anchor after the warp) and a base and amp blended from the nearest few; `height_at` adds fractal noise, flattens at anchors and pulls the edge of the world under the sea; `node_at` places a node from the biome's `nodes` table and a clumping noise (an **outcrop** only where `GameMine.ore_at` finds ore within `outcrop_depths` of the surface, and of that ore); `tile` and `chunk` assemble them. Noise comes from `_lat`, an integer mix: **do not use Godot's `hash` of nearby integers for a new roll here, it is correlated between neighbouring tags** (it left forests without herbs). A new place needs a biome that has a `surface_of` entry and a position on the map; a new node kind needs an existing material (or `""` for an outcrop) and an entry in a biome's table (the validator checks). `tests/test_game_worldgen.gd` checks the anchors, the seed, the land, the sea, the nodes and that nothing of the dynasty's moves. Not built: a screen, rivers and lakes, roads between anchors, respawning and harvesting nodes, other worlds.
- **World spaces.** `GameSpaces` (core, no UI; `data/world/spaces.json`, checked by `tools/check_data.gd`) gives every place a space id and a position, so the text game and the sandbox name places alike. Ids are paths: `world` (the open world; the same id `GameWorldGen.MINE_SITE` and the mine use), `world/<place>` for each place in `world.json` (`kind_of_type`: a town or wilds is an `area` of the open world round its anchor tile, a dungeon an `interior` behind a door at its anchor), `world/<town>/<service>` for each of a town's services and `world/<start town>/house` for the family house (interiors of the town, their doors `service_doors`/`house.door` tiles east and south of the town's middle, which the validator keeps on the town's cleared ground and apart). `space(id)` is `{id, kind, name, parent, place, door: {space, x, z}, radius}`; `map_tile(id)` is its door tile on the open world; `at_tile(x, z)` the area a tile stands in; `where(d)` the heir's `{space, place, x, z}` from `d.world.location`; `route(from, to)` the way as `leave`, `walk` (with `from`, `to`, `tiles`) and `enter` steps through the space the two share; `road_walk(a, b)` one of the text game's roads as a walk with its years. Built once from data and the anchors (tests that change the data clear `_cache`, `_spaces` and `_order`); nothing is saved, no dice. A new place gets its space by being in `world.json`; a new service needs a name and a door here. Not built: anything inside an interior (rooms, a floor plan), the heir's position between places, the underworld and other realms as spaces, and travel that walks the route.
- **World events.** `GameWorldEvents` (core, no UI; `data/world/world_events.json`, checked by `tools/check_data.gd`) is the wars, famines, pestilences, fairs and golden ages that come and go. One runs at a time: `GameDynasty.world_event` is `{id, began, until}` while one runs or `{id: "", until}` while the world rests after one (saved only when not empty, loaded clean by `load_state`). `on_years` (called from `_pass_years` right after `world.advance`, so every way of passing time reaches it) ends a running event at its `until`, rests `rest_years`, and for each free whole year rolls `rolled(d, year)`: nothing in the first `grace_years`, else `chance_per_year`, picked by `weight` among the events whose `min_gen`/`max_gen` window holds `era_gen()`; `length` picks its years. **Every die is keyed on the seed and the year, never the dynasty's**, so the rest of a life draws exactly as before. While one runs, `mult(d, key)` (1.0 otherwise, so a quiet world multiplies by exactly 1) scales numbers the rules already have (`EFFECTS`): `price_mult` (`GameItems.price_mult`, so shops, the temple and cures, and `potion_price`), `hunt_gold_mult` and `hunt_xp_mult` (`finish_battle`), `work_gold_mult` (`work`), `disease_mult` (`GameDisease._expose`, same die, a higher chance). Beginnings and ends are told in the journal and counted in the flag `world_events_seen`; the life screen names a running event beside the weather and the Statistics tab once one has been seen. **This was a balance change**: the autopilot lives through events, so the six autopilot-life digests in `tests/fixtures/round_baseline.json` were recaptured (every fight scenario is unchanged); the harness went from 4.1% to 4.0% battle deaths over 960 lives. A new effect needs its name in `EFFECTS` and a place that multiplies by `mult`. Not built: events that change which creatures a hunt meets or how strong they are, events tied to a place, the player or the factions causing or ending one, and more than one at a time.
- **Day and night.** `GameDay` (core, no UI, no screen yet; `data/world/daycycle.json`, checked by `tools/check_data.gd`) puts a day on the world clock. `GameDynasty.world_seconds` (saved only when above 0, loaded clean by `GameDay.load_seconds`) is added to by `GameClock.feed` only while the clock runs; a day is `day_seconds` of it (an abstract rhythm, not tied to the length of a year) from `start_phase`. `phase` is 0 at midnight and 0.5 at noon, `sun_height` is `-cos(2*pi*phase)` and `sun_light` ramps 0 to 1 across `twilight` either side of the horizon, so `phase_name` is night, dawn, day or dusk; `is_night` is the sun's light under `night_below` (weather never makes a night). **The weather is the world's own** (`world.weather_id`, rolled each span with the dynasty's dice by `GameWorld.advance`, and what battles use): `weather_look` gives each weather a `light` share, `fog`, `precip` (none, rain or snow) and `sight`; every weather in `world.json` needs one (the validator checks). `look(d)` is `{phase, hour, sun, light, tint, fog, precip, weather, season, night}` for a renderer. `view(d, targets)` is `GameBehaviour.world_view` plus `sight_mult`, which `step_all` multiplies into how far a creature sees (absent means 1, so every other caller plays as before), and `spawn_context` is `GameSpawn.context_at` with the current night. Pure: no dice, the autopilot never feeds the clock, so it moves nothing; `tests/test_game_clock.gd` drops `world_seconds` from its digest as the clock's own. Not built: a screen, weather spells shorter than a year, creatures that sleep, hunts (the text game) that use the hour or the weather.
- **Mining.** `GameMine` (core, no UI, no screen yet; `data/mining/mining.json`, checked by `tools/check_data.gd`) is the ground as data: a **site** (a place id) has rock **layers** (hardness, whether ore forms), three **zones**, and **ore veins** (each `block`-sized cube may hold one vein, a sphere picked from depth `ores` bands by weight and `chance`; `ore_at` looks at the 27 nearby blocks), all a pure function of `seed_value`, the site and the cell, so the same seed gives the same ground and no dice are drawn. Depth y counts down from 0; `age_at` says which Age a depth is (digging goes back in time). **Digging** (`can_dig`, `dig`) needs open air beside the cell (any cell at depth 0, otherwise a dug neighbour), costs `effort` (hardness times the stage's `hardness_mult` over Strength) and puts ore into `GameCraft` stores. Each dig adds strain to its `region` (more the deeper); `stage_of` gives the stage (softer rock, fatter veins through `ore_bonus`, read by `ore_here`) and the last stage (`gateway_stage`) records a **gateway** at the cell that tipped it. `GameDynasty.mine` is `{site: {dug: {"x,z": [[y0,y1]]}, strain: {"rx,rz": f}, gateways: [...]}}`, saved only when not empty and loaded clean by `GameMine.load_state`. A new ore needs a material the game has (and a depth band), and a vein radius times the biggest `ore_bonus` under one block (the validator checks, and that no depth where ore forms is left without an ore). Nothing asks it yet from a screen; `tests/test_game_mine.gd` checks that the autopilot digs nothing. Not built: a screen, the underworld space, vaults and ruins, tools, hazards.
- **Gathering and crafting.** `GameCraft` (core, no UI; `data/items/craft.json`, checked by `tools/check_data.gd`; screen `ui/play/craft_panel.gd`, opened from the House panel's Workshop button) has **no recipe grid: a piece is composed** from a form (`GameLoot`'s), a material in the stores and up to `max_essences` essences, and the result is an id `GameLoot.build` reads, so made and dropped items are one system (`GameCraft.plan` says what a choice would make and why not, nothing spent; `craft` spends and puts it in the pack; the plan's quality is the made piece's quality). An essence is an affix kept in a bottle: `rarity_by_essences` maps 0 to 3 essences to common, fine, rare, legendary, and the validator refuses a mythic. **Stores** are `GameDynasty.stores` (`materials`, `essences`, and the `crafted` count), saved only when not empty and loaded clean by `GameCraft.load_stores` (unknown ids, non-positive or wrong-typed values dropped). **Gathering is asked for by the screens**: `GameLoot.search_dead` calls `GameCraft.after_search` (one die per entry in a creature's `drops`, keyed on the seed and the hunt, never the dynasty's) and the battle screen calls `GameCraft.after_legend` (a boss always leaves its parts, once per legend by a flag); `salvage` breaks pack gear into half its material and a made piece's affixes as essences. Crafting needs `needs_service` (a forge) at the heir's place; salvage works anywhere. A new hunted creature needs a `drops` entry and a new material needs something that drops it (the validator checks both). Quality is `quality_per_level` times level plus `craft_quality` traits plus a keyed roll; a piece takes `GameLoot.grade_of(gen)`. `tests/test_game_craft.gd` checks that an autopilot life gathers and makes nothing. Not built: foraging as an action, a workshop track, repairs, consumables.
- **Carry limits.** `GameCarry` (core, no UI; `data/items/carry.json`, checked by `tools/check_data.gd`) is how much the heir can carry: `capacity` is `base_capacity` plus `per_strength` times Strength, `carried` is the weight (item 42) of the pack, what is worn and `potion_weight` per healing potion. `GameCarry.can_carry` gates the voluntary pickups: `GameItems.buy` refuses (`why_not` gives the line), and `GamePlague._find` and `GameLoot._give` sell what does not fit where it lies (`sell_find`). `GameDynasty.give_item` (events and quests) always takes, so a heir can be over the limit (`burdened`); there is no other penalty yet. `GameCarry.drop` leaves one item from the pack (never worn gear); the pack screen's Drop button asks twice for gear. Potions are not gated. The capacity is set so the autopilot is never refused (`tests/test_game_carry.gd` plays it and checks): a change to the capacity, to weights or to what the autopilot carries that makes it refuse a purchase is a balance change. A new way to pick something up should ask `GameCarry.can_carry`. Not built: a heavy-load penalty, party and house stores, bags.
- **Loot generator.** `GameLoot` (core, no UI; `data/items/loot.json`, checked by `tools/check_data.gd`) builds items that are in no list: an item **is its id**, `gen:<rarity>:<slot>:<form>:<material>:<affixes joined by +, or ->:<mythic or ->:<grade>:<quality 0-9>`, and `GameLoot.build` rebuilds it from the forms, `GameMaterials`, affixes and rarities, so a save holds only the id (a damaged or unknown id builds nothing and loads as an unknown item). `GameItems.item_def` returns the built item for a `gen:` id, so everything that reads items (wearing, selling, `tags_of`, `GameFeats.weapon_kind`) works unchanged. **It grows with the world**: `tier_ceiling(gen)` opens material tiers by generation (`tier_gens`), `grade_of(gen)` adds +1 every `grade_gens` generations after the top tier (up to `max_grade`) and strengthens every effect. Rarity is a weighted roll out of `weight_total` (a million; mythic is 10); a rarity may reach `overreach` tiers above the ceiling. **Drops are asked for by the screens**, never by the rules of a life: `GameLoot.search_dead` (the loot panel and the battle screen, in place of `GameFinding.search_dead`) rolls once per foe on its own dice (`drop_chance`) and `after_legend` gives a slain legend one drop at the legend boost, once per legend by a flag, so the autopilot (`GameBot` never calls them) and the golden digests do not move; `tests/test_game_loot.gd` checks that an autopilot life meets no made item. A new form, affix or mythic is data (the validator checks stats, slots, tags and that every slot has forms, tier 1 prefixes and suffixes, and a mythic); a new stat an affix uses must be in `items.json` `effect_labels`. Made gear has no art yet (it keeps the old block look). Not built: scrapping, drops from events and chests, and crafting on the same parts.
- **Raids.** `GameRaids` (core, no UI; `data/creatures/raids.json`, checked by `tools/check_data.gd`) is asked by `GameDynasty._pass_years` (after `GameRanch.on_years`), so every way of passing time reaches it. A house can be raided if it has **something worth taking**: animals in the pens, or a house that has been built (`house_value`: `house_value_share` of what each track's levels cost). A plain house is a target too once the heir holds `plain_min_gold` (`has_purse`), but only a small one: with no animals and nothing built the chance is the flat `plain_chance` a year whatever the purse holds (a purse that scales the chance would be a raid every year for the autopilot, which holds thousands, and each raid pays XP); with no purse either, the chance is 0 and nothing is rolled. This **was a balance change**: the autopilot holds gold, so it now meets about 0.8 raids a life, and the five autopilot-life digests in `tests/fixtures/round_baseline.json` were recaptured (every fight scenario is unchanged); see PR for the before and after harness numbers. Each whole year the clock crosses rolls on dice keyed on the seed and the year, **never the dynasty's**; the chance is `base_chance` plus `per_stock_gold` times the `valuables` (stock plus house), capped at `max_chance`, and cut by `deterrence` (the guards, `GameRanch.guard_cut`, up to `deter_share`; no animals, no guards, until hired guards exist). A raid is an **event** marked `raid: true` in `events.json` (`raid_thieves`, `raid_rustlers`, `raid_beasts`, `raid_burglars`, one per kind in `raids.json`): `GameEvents.is_eligible` never offers them while exploring, `GameRaids.on_years` begins one (never while another waits, and only a kind with something to take: thieves need gold, burglars a carried item, rustlers and beasts an animal; `GameEvents.explore` no longer overwrites one that came with the year), and the heir settles it on the event screen. The outcome effect `defend: <kind>` is trusting the guards: `GameRaids.defend` beats the raid off with `beat_off_chance` (0 with no guards, up to `beat_off_max`) or it takes what it came for (thieves a share of the gold, cut by the guards' `guarded_loss`; burglars a carried item; rustlers an animal; beasts kill one). Other choices pay, trick (a skill check, failing into `defend`) or ride out and fight (a `fight` outcome). Not built: renown and infamy changing the chance, hired guards and walls, and raiders beyond these four.
- **Farm animals.** `GameFarm` (core, no UI; `data/creatures/farm.json`, checked by `tools/check_data.gd`) is the worth of the creatures flagged `farm: true` in `creatures.json` (sheep, cattle, pigs, chickens, goats, geese and horses, with art in `data/art/creatures.json` held to the usual style). **Farm animals are never fought and never found beside the dead**: the hunt's and the events' creature pools filter `farm` out (`GameDynasty.start_hunt`, `GameEvents._in_era`/`_creature_for`, the event validator), so every seeded fight and the golden digests are unchanged. They are **bought young at a town's market** (`GameFarm.buy`, flat prices, the name and sex keyed on the seed and what is kept, a bird skipping its egg), raised and bred like any creature (they have sizes in `ranch.json` and families in `breeding_rules.json`), give **wool, milk or eggs** each year through `work_of` (the pay follows the season, `season_mult`, and how well the animal is kept, `mood_scale` from the `mood_floor` to 1: `GameFarm.yield_mult`, read by `GameRanch.yearly_work`; wild creatures' work is untouched), and can be **slaughtered** for meat and hide once, past their egg (`GameFarm.slaughter`, paid by stage and mood, ending the animal). The Creatures tab has the Market (buy buttons, shut away from a town with the reason shown) and a Slaughter button asking twice. A new farm animal needs creature data with `farm: true`, art, a size, a family, a market price and meat and hide (`GameFarm.validate`). A horse gives `haul` work (a plough and cart, not wool or milk) and is **never slaughtered**: `farm.json` `settings.no_slaughter` lists such species and `GameFarm.slaughter_value` returns 0 for them (the validator wants every farm animal either to have meat and hide or to be listed there). Not built: bees (a hive needs its own rules: no sex, no pairs), the market varying by place, and trade.
- **Companions in the world.** `GameCompanions` (core, no UI, no screen yet; `data/companions/world.json`, checked by `tools/check_data.gd`) gives a hired companion (`GameParty` member) an **order**: `follow` (default, nothing saved), `stay`, `gather` or `guard`. `set_order` writes it on the member (`order`, erased for follow) and `GameParty.from_dict` loads it through `load_order` (unknown or mistyped means follow). Where companions stand is **runtime, not saved**: `agents_for(d, hx, hz)` puts one agent per member beside the heir and `reconcile` follows hires and departures. `step_all(d, agents, view, tick)` returns `{agents, events}` (inputs untouched): `view(d, hx, hz, threats, router)` is `GameBehaviour.world_view` plus the heir, threats and an optional `GamePath.router`, and movement uses `GameBehaviour._route` and `_move`. An order change resets the work and sets the post to where the agent stands. Follow keeps `follow_min`..`follow_max` (hysteresis), a ring offset by index so they do not stack, and teleports past `follow_catchup`; guard intercepts the nearest threat within `guard_radius` times the class share of the post, is clamped to that reach and sends one `alert` per sighting; gather `scan`s nodes within `gather_radius` of the post (nearest first, ties by x then z), plans a few, claims one so two companions do not share a trip, works `gather_ticks` and adds the node's material times the class share (`classes`, `default` otherwise) to `GameDynasty.stores`. `GameDynasty.gathered` (`{"x,z": world year}`, saved only when not empty, loaded clean by `load_gathered`) marks a node until `regrow_years` have passed. No dice, no combat; the autopilot never steps companions or gives orders (`tests/test_game_companions.gd` checks). Every companion class needs work shares in `classes` (the validator checks). Not built: a screen, guards that fight, loads carried and returned, other work, night watch.
- **Titles.** `GameTitles` (core, no UI) reads `data/titles/titles.json`: each title has a `kind` (`personal`, ending with the heir and kept in their lineage record, or `house`, kept by the dynasty), an `about` that says how it is earned, a `when` condition read from the dynasty's own state (`stat` with `gte`/`lte` from `GameTitles.STATS`, `boss`, `boss_by_heir`, `flag`, `trait`, `class`, `race`, `family`, and `all`/`any`/`not`) and an optional `perk` (only `persuasion`, cheaper shops, while worn; `GameItems.persuasion` adds it). Earned ids are saved only once there is one (`GameHeir.titles`, `title_worn`, `GameDynasty.house_titles`, and `titles` in a lineage record) and load cleaned of anything unknown. **Earning is asked for by the screens** (`GameApp.show_state` and the life screen's `_changed` call `GameTitles.announce`), never by the rules of a life: the autopilot and the golden scenarios earn nothing and draw no die for it, so their results do not move. A new condition kind needs its branch in `met` and `_cond_problems`; `GameTitles.validate` is part of `tools/check_data.gd`. The Chronicle's Titles tab lists earned and unearned titles and puts one on or off. `tests/test_game_titles.gd` checks all of it, including that every title can be earned.
- **Achievements.** `GameAchievements` (core, no UI; `data/achievements/achievements.json`, checked by `tools/check_data.gd`) keeps the dynasty's milestones: each is a `count` about the whole house (`COUNTS`: generations, years, ages, legends, legend_kills, heirs, house, creatures, bred, crafted, built, heirlooms, titles, gold, milestones) reaching a `goal` (or `goal_from: house_max`). Once reached it is on `GameDynasty.achievements` for good (`{id: {gen, year, heir}}`, saved only once there is one, loaded clean and in the data's order by `load_state`), even if the count later falls. A milestone may award a house title: the title's `when` is `{achievement: id}` (a test kind in `GameTitles`), and the validator wants the two to name each other. **Reaching is asked for by the screens**: `GameTitles.announce` calls `GameAchievements.announce` first, so a milestone and the title it brings are told in the same pass; `GameTitles.update` alone does not. The rules of a life never ask, so the autopilot reaches nothing and no die is drawn. The Chronicle's Milestones tab draws `describe(d, id)` (who reached it and when, or `have of goal`). A new count needs a branch in `count`, an entry in `COUNTS` and a milestone that uses it. An Age is `age_length` (1,100) generations, so Age milestones are far apart. Not built: rewards other than titles, and milestones for one heir's deeds (those are personal titles).
- **Faction reputation.** `GameFactions` (core, no UI; `data/factions/factions.json`, checked by `tools/check_data.gd`) is how six factions judge the heir by their ancestors. **A standing is worked out, never saved**: `remembered(d)` is the living heir (`ago` 0) and every dead heir `history` keeps in full (heirs folded into the Ages are forgotten); each faction's `remembers` rules (`HEIR_RULES`: class, level, battles, kills by creature or tag, gold, cause, titles; `each` per time it applies, within `cap`) weigh each of them, an ancestor's share fading by the faction's `memory` per generation, and its `house` rules (`HOUSE_RULES`: echo of glory or infamy, bosses slain, milestones) weigh what belongs to the whole house. `standing(d, id)` is -100 to 100, `rank` the highest of `ranks` it reaches (hostile, wary, neutral, trusted, honoured), `reasons` what was weighed, strongest first. At `boon_rank` or better `take(d, id)` gives the living heir the faction's gift once in their life, in a town (gold scaled as prices are, potions, XP by level; doubled at the top rank; marked in `GameHeir.boons`, saved only once there is one), and at the top rank the faction confers a personal title whose `when` is `{faction: id}` (a test kind in `GameTitles`; the validator wants the two to name each other). No dice. **Nothing in a life reads a standing**: no price, hire or fight, and the autopilot takes no gift, so results and the golden digests do not move. The Chronicle's Factions tab draws `describe(d, id)` and calls `take`. A new rule kind needs a branch in `heir_points` or `house_points`, its name in the list and a check in `_rule_problems`. Not built: standings changing prices, hires, quests or who attacks (each would be a balance change), the heir acting to win a faction over, and faction quests.
- **Tutorial.** The first-heir tips are chosen by `GameTutorial` (core, no UI) from the dynasty's own state, using the rules and text in `data/ui/tutorial.json`; nothing of it is saved, so it works on old saves. Only whether the tips are on lives in `user://settings.cfg`. The strip (`ui/play/tutorial_tip.gd`) is one row on purpose: a phone at large text has no height to spare. A new tip needs a `when` that includes `first_generation` and text of 125 characters or fewer; `tests/test_game_tutorial.gd` checks both. The open world's tips are the steps with screen `sandbox` (move, dig, wood, build, room, orders, night; `GameTutorial.SCREENS` lists the screens): `current(d, "sandbox", ctx)` answers from dug ground, stores, `GameBuild`, the party's orders and `GameDay`, and takes in `ctx` the yes-or-no facts only the screen knows (`GameTutorial.CONTEXT`, now just `moved`; absent or mistyped is false). A new question goes in `PREDICATES` with a branch in `holds`; a new placeholder in `fill` (`{home}`, `{claim}`). No sandbox screen shows them yet.
- **Text in data.** The fight's log lines are in `data/text/battle.json`, found by key through `GameMessages.line(key, {placeholders})` (core, no UI). Add a line as a new key and a call, never as a string in code: `tests/test_game_data.gd` spells out every line word for word, fails if a `_say("...")` literal returns to `game_battle.gd`, and `tools/check_data.gd` fails on a key the code asks for that the catalog lacks, or one nothing asks for. Not yet moved: the life actions' messages in `game_dynasty.gd`, `game_events.gd`, `game_party.gd` and the rest of `core/game` (roadmap item 28 goes on).
- **Localisation.** `GameLocale` (core, no UI; `data/text/locales.json`, checked by `tools/check_data.gd`) chooses the language of the text that is in data. `text(catalog, key, source_text)` returns the source line in the game's own language (`source`, English: so nothing changes for a game that never switches, and the golden digests do not move), a translation's line when the chosen locale has one **using exactly the source's `{placeholders}`** (any order), the source line otherwise, and for the **pseudo-language** a line made on the fly (`pseudo`: every letter accented from `pseudo.map`, padded by `expand`, bracketed, placeholders untouched). Catalogs are `battle` (`data/text/battle.json`, read through `GameMessages.line`) and `tutorial` (the tips by step id, read in `GameTutorial.current`). A translation is `data/text/locales/<id>/<catalog>.json` as `{"lines": {key: text}}`; `check(id)` lists unknown keys, wrong placeholders and missing lines, and the validator fails a listed locale that is not complete. The choice lives in `settings.cfg` (`UiSettings.locale`, set at start by `GameApp._ready`), never the save; the menu shows a Language row only when `offered()` has more than one (the pseudo-language is `hidden`, chosen by `locale="pseudo"` in the settings file). `tests/test_game_locale.gd` checks the font has `sample_chars` and the pseudo letters; `tests/test_game_mobile.gd` lays the screens out in the pseudo-language and holds the tip strip to `tip_max_height_share` of a phone screen (`data/ui/mobile.json`), because a wrapped tip is never off the screen, it eats it. **Most text is still in code and is not translatable** (roadmap item 28); only English ships. A new catalog needs a branch in `source_lines` and a reader that calls `GameLocale.text`.
- **Save slots.** `GameSaves` (core, no UI) owns the slot files: slot 1 is the original `user://dynasty_save.json`, the others add `_2`, `_3` (`balance.json` "save_slots"). `GameDynasty.save_path` stays "the file in use"; `GameApp.use_slot` points it at the chosen slot, so saving and loading are unchanged. Saves are written atomically and keep the one before as `.bak`, which loading falls back to. A backup is `GLBK1:` + base64 of the gzipped save, copied to and from the clipboard (`ui/play/clipboard.gd`, which tests fake) or written to and read from a `.glsave` text file holding the same block (`GameSaves.export_file`/`import_file`; `ui/play/file_picker.gd` uses the platform's file dialog where there is one, else the Downloads or `user://exports` folder, and tests fake it); `GameSaves.import_text` checks the shape before anything is loaded. If the save format gains a required key, add it to `GameSaves.REQUIRED` only when old saves have it too. The file is written by `GameDynasty.to_save()`: `to_dict()` (the shape the golden digests use, never changed by this) at the version in `GameSaveVersion.CURRENT`, plus a fight in progress under `"battle"` (`GameBattle`/`GameRound` `to_dict` and `restore`, in Godot's exact binary encoding as base64, values only), so a game closed mid-fight reopens in the same fight and plays on as if never saved. `GameSaves` runs `GameSaveVersion.upgrade` before `from_dict`: one tested step per version; a save from a newer game is turned away. A format change needs a new version and its step.
- **Error reports.** `GameReport` (core, no UI; `data/ui/report.json`, checked by `tools/check_data.gd`) makes a report the player can pass on: `build(d, env, errors, note)` is `{format, game, save_version, env, note, errors, journal, save}` and `to_text` packs it as `GLER1:` + base64 of the gzipped JSON. **The game never sends it**; the player copies or saves it. Of `env` only the keys in `env_keys` are kept (so whatever a screen offers, nothing else about the device leaves), and the note, errors and journal are cut to the limits in `settings`. The save is `to_save()`, a fight in progress included; `d` may be null when no house could be loaded. `from_text` returns `{ok, error, report}` cleaned to the same shape and limits, and turns away (never crashes on) a block that is not a report, is damaged, is from a newer `FORMAT`, or whose save `save_problem` says cannot be played; `dynasty(report)` loads the house through `GameSaveVersion.upgrade` and `backup_text(report)` gives the save as a `GLBK1:` backup the game's own Load reads. `GameErrorLog` (core, extends Godot's `Logger`) remembers the last errors, warnings and script errors as lines (`install(keep)`, `recent()`, `clear()`, `remove()`), in memory only, guarded by a mutex because errors can come from any thread; it is installed only when the player has switched the menu's **Error log** on (`UiSettings.error_log_on`, off by default, in `settings.cfg`; `GameApp.set_error_log` installs or removes it, and `_ready` installs it for a player who asked). The menu's Problems section also has **Report a problem** (in every menu mode, the title's too), which opens `ui/play/report_panel.gd`: it shows `text.never_sent` and `text.holds`, takes a note, and copies the report (`Clipboard`) or saves it as a `.glreport` file (`FilePicker.save` with its own filter); the report is built from the house being played (none at the title), `ui/play/report_env.gd` (`ReportEnv.facts`: the only place device facts are gathered) and the log. A new fact about the device goes in `env_keys`, in `ReportEnv.facts` and in `text.holds`; `tests/test_game_report_ui.gd` fails if the screen offers a fact a report may not keep. **A bad close is noticed**: `GameSessionMark` (core, no UI) writes a mark file when a session begins (`GameApp._ready`, beside the settings file: `session_mark_path`) and removes it when the session ends properly (the window closing, the app going to the background, `_exit_tree`); a mark still there at the next start sets `GameApp.closed_badly`, and the title then shows one row saying so with Report a problem and Dismiss. The mark holds nothing but the word "running". The error log is memory only, so a report made after a crash carries the save and not that session's errors. Not built: reading a report inside the game, and keeping a crashed session's errors.
- **Family house.** `GameHouse` (core, no UI) holds the three upgrade tracks, Hall (companion places), Yard (training XP) and Ranch (pens, hatchery and nursery for the creatures, see Creature growth), bought with the heir's gold and stored on the dynasty as `house` (only once something is bought). Costs and effects are in `balance.json` (`house_*`; the Ranch's effects are in `data/creatures/ranch.json`). Use `GameParty.max_size(d)` for the party's places, never the base setting, so the Hall counts. The House button on the life screen opens `ui/play/house_panel.gd`, which only calls `GameHouse.buy` and draws the rows; a row that cannot be built is disabled, with its reason shown as text under it.
- **Heirloom upgrades.** `GameHeirlooms` (core, no UI; `data/items/heirlooms.json`, checked by `tools/check_data.gd`) lets each heir have each of the house's heirlooms (`GameDynasty.heirlooms`, `{name, boss, gen}`) reworked once in their life: `upgrade(d, index)` needs a place with the `needs_service` service (a forge) and gold (`cost`: `cost_base` times the square of the level bought, scaled by the generation as prices are), raises the heirloom's `level` (to `max_level`), and records `worked_gen` and the heir's name in `smiths`; a second rework in the same generation is refused, so an heirloom grows over generations. `GameDynasty.heirloom_bonus()` is now `GameHeirlooms.total_bonus(d)`: the count times `heirloom_bonus` **worked out exactly as before**, plus `level_bonus` per level of the first `heirloom_max` heirlooms, so a hall with no levels gives the same number to the last bit (`tests/test_round_determinism.gd` holds). The three keys are written only once an heirloom is reworked and load cleaned by `load_list`. No dice; the autopilot reworks nothing. The House panel shows an Heirlooms button only when the house holds one (`ui/play/heirloom_panel.gd`). The validator refuses settings under which a full hall would more than double an heir's power. Not built: heirlooms that do anything but give power, heirlooms from anything but a legend, and losing one.
- **Family tree.** `GameFamilyTree` (core, no UI) reads the dynasty's `history`, living heir and echoes into one entry per generation. Older heirs folded into the Ages are counted only. The chronicle's Family Tree tab (`ui/play/chronicle_panel.gd`) draws it; it has no tooltips, so the mobile suite needs nothing more.
- **Statistics.** `GameStats` (core, no UI) works out the dynasty's numbers from `GameAges` and the kept heirs. The chronicle's Statistics tab draws them. Each Age row keeps `gold_sum` and `gold_known` (the gold of its heirs at death), so the average per Age survives folding; the heirs kept in full also list their own gold.
- **Sex.** `GameSex` (core) gives every heir, spouse and child a sex: the founder picks it at the start, a spouse is always the opposite sex, and children are rolled from their own seeded dice (never the dynasty's main dice, so no life changes). Old saves are filled in on load (`GameDynasty._fill_sexes`). The golden digests drop the `sex` key (`Scen.drop_sex`, in place: copying would break the shared lists those digests rely on).
- **Accessibility.** Three yes-or-no options in `settings.cfg` (`UiSettings.ACCESS_KEYS`), set from the menu's Accessibility row. UI code takes colours from `Kit.good()`, `Kit.bad()` and `Kit.dim()`, never `Kit.GOOD`/`BAD`/`DIM` directly, and animations take their time from `UiSettings.motion_time()`.
- **Battle art.** The battle screen draws the hero, companions and foes from pixel sprites kept as text grids in `data/art/` (`docs/ART.md`), turned into textures by `ui/play/sprite_art.gd` (rendering only, cached). A figure is the class's 24x40 figure in the race's colours with the race's under and over layers, wearing a shirt from `data/art/shirts.json`: one picked from who they are unless the player chose one on the Looks panel (`ui/play/looks_panel.gd`, `GameDynasty.set_shirt`; saved as `shirt` only once chosen), and the heir in their gear: `data/art/gear.json` gives each weapon and armour a finish, a glow or a cape, and says per class where the weapon is and which palette keys are metal, leather, blade and wood. Art follows the style in `docs/ART_STYLE.md`, whose numbers are in `data/art/style.json` and checked by `SpriteArt.style_problems` (outline, stray pixels, colour cap, size, margins, standing on the ground; part of `SpriteArt.validate`, so `tools/check_data.gd` runs it); a new sprite must pass `tests/test_game_art_style.gd`. The textures `SpriteArt` hands out are regions of shared atlas pages (`ui/play/texture_atlas.gd`): use them as any texture, and wrap the building of a screen's many figures in `SpriteArt.begin_batch()`/`end_batch()` so the pages upload once. Anything without art keeps the old block. Each sprite figure stands in a `ui/play/figure_pose.gd` holder that breathes and plays the battle's events as moves (attack, cast, hurt, dodge, guard, fall), stilled by reduced motion. The fight is drawn in front of the land it happens in: `ui/play/scenery_art.gd` paints the place's scene from `data/art/scenery.json` (a scene per biome, place extras, weather and season layers) with its own dice seeded from the place, never the dynasty's. `tests/test_game_art.gd` checks every creature, class and race has art, `tests/test_game_gear.gd` the gear, `tests/test_game_poses.gd` the poses and `tests/test_game_scenery.gd` every place's scenery; `tools/art_sheet.gd` draws it all on one sheet.
- **Cosmetic randomness.** Anything the view randomises for show (a painted scene's scatter, particles, idle timing, camera shake) draws from `CosmeticRng` (`ui/play/cosmetic_rng.gd`: `keyed(key)` rolls the same every time, `loose()` differs each run), never from the dynasty's `rng` and never from Godot's global dice. `tests/test_game_cosmetic.gd` scans `ui/play` for both and plays fights through the battle screen to check they end exactly as the same fights with no view.
- **Gamepad and keyboard menus.** `ui/play/pad_focus.gd` (a node `GameApp` adds before the screens, `app.pad`) makes the ordinary buttons usable without a pointer. The engine moves a focus with the d-pad, stick or arrows by itself; `PadFocus` adds joypad A to `ui_accept` and B to `ui_cancel` (the engine binds neither), turns **pad mode** on at the first pad or arrow input (that first input only shows the focus), focuses the first button of the top layer (`layer()`: the open panel with a `back_close` meta, else the screen), brings back a focus that is lost when a screen is rebuilt or that strays out of the open panel, makes scroll areas follow the focus, sends `ui_cancel` (B, Escape) to `GameApp.go_back` and Start to the menu. A click or a touch turns pad mode off and drops the focus, so the ring (`Kit.focus_ring`, on every `Kit.button`) is never seen with a mouse or a finger and the stored screenshots do not change. A screen's own `_unhandled_input` for `ui_cancel` (the battle's) still comes first. Not built: aiming at a foe or an ally in a fight (those are tapped figures, not buttons), button prompts, and remapping.
- **Graphics settings.** `ui/play/graphics_settings.gd` (rendering side; `data/ui/graphics.json`, checked by `tools/check_data.gd`) holds the quality presets (`low`, `medium`, `high`: `pixel_scale`, `effects` as off, some or all, and `fps_cap`, 0 meaning uncapped) and the **battery saver**, which lies over whichever preset is chosen (its frame cap unless the preset's is lower, effects off, the engine's low-processor mode). The choice is in `settings.cfg` (`graphics`, `battery_saver`), never the save; an unknown stored preset falls back to the device's default (High on a computer, Medium on a phone). `current()` is what is in force, `effect_on(name)` asks whether an effect listed in `effect_levels` is drawn, and `apply()` (called at start and by `GameApp.set_graphics`/`set_battery_saver` from the menu's Graphics rows) sets `Engine.max_fps`, `OS.low_processor_usage_mode` and `SceneryArt.particles_on`, forgetting the painted scenes when that changes. With the particles off `SceneryArt` still rolls their dice (`Canvas.mute`), so the rest of a scene is pixel-for-pixel the same. A new effect gets a name in `effect_levels` and asks `effect_on` where it is drawn. `pixel_scale` has no reader until the 3D renderer exists.
- **Sound.** `ui/play/sound.gd` (view side, a node `GameApp` adds once as `app.sound`; `data/ui/sound.json`, checked by `tools/check_data.gd`) makes every sound from data: **there are no audio files**. A cue or track is a `wave` (sine, triangle, square, saw, noise), `notes` (MIDI numbers, 0 a rest, a list a chord), `step`, `attack`, `release`, `volume` and an optional `slide`; `samples(def, rate)` (pure, static; noise rolls `CosmeticRng.keyed`) builds it, `stream(name)` turns it into an `AudioStreamWAV` the first time it is wanted and keeps it (tracks loop, and every note ends in silence so the loop does not click). **What plays:** the battle screen's `_play_one` hands each event to `app.sound.event`, and `cue_for(ev)` reads the `events` table (a battle event type from `battle_events.json` to a cue, with `variants` on a field such as `crit` or `side`; an unlisted event is silent); `_show_result` plays `results` (victory, defeat); `GameApp._sound_state` (from `show_state`) plays the `stings` once per death (`succession`) and at the saga's end (`ended`), and asks for the music of `track_for(dynasty)`: the title's, a fight's, silence for an ended saga, else the track `ages` lists for `age_number()`, going round again after the last. **Settings** are in `settings.cfg`, never the save: `sound` and `music` (on unless the file says off) and `sound_volume`, `music_volume` (a step of `levels`, the default when unknown); the menu's Sound effects and Music rows offer Off and the steps (`GameApp.set_sound`, `Sound.choose`). Nothing in `core/game` knows of it and it draws none of the dynasty's dice, so a fight plays the same heard or not (`tests/test_game_sound.gd` compares). With no audio device (the engine's Dummy driver: headless, the screenshot tool) the streams are built but the players are never started (`has_output`); tests read `cue_log` and `music_log`. A new cue or track is data and must be played by something (the validator refuses an unused one and caps the seconds built); a new battle event is silent until it is in `events`. Not built: recorded music or samples, crossfades, sounds for buttons and life actions, and nobody has listened to it on a real device yet, so the notes and volumes are a first guess.
- **Input for a world.** `ui/play/world_input.gd` (input side; `data/ui/input.json`, checked by `tools/check_data.gd`) holds the open world's actions (`world_move_*`, `world_cam_*`, `world_zoom_in/out`, `world_dig`, `world_build`, `world_interact`, `world_cancel`, `world_menu`, `world_pan`) and their bindings: keys by Godot's names, mouse buttons, gamepad buttons and `[axis, -1 or 1]` gamepad axes. `install()` (called by `GameApp._ready`) puts them in the engine's input map under those names, so a sandbox screen asks for an action and never a key; the engine's `ui_*` actions are untouched. The validator wants every action reachable from the keyboard or mouse and from a gamepad (`pointer_only` excepted), no binding on two actions, and names the engine knows. The arithmetic is pure and static: `stick` (radial dead zone), `move_vector` (a diagonal no faster), `touch_stick`, `is_tap`, `zoom_after`, `pinch_zoom`, `facing` (one of eight `FACINGS`), `cell_ahead` (what a gamepad or keyboard acts on) and `camera_follow_seconds` (0 with reduced motion). `read()` gives `{move, look, zoom, dig, build, interact, cancel, menu}` from the input map. Touch has no bindings: the screen that tracks fingers calls the arithmetic. Nothing reads any of this yet: there is no sandbox screen, and pointing at a tile with a mouse or finger needs the renderer's projection, which is not chosen.
- **Touch.** `ui/play/touch_hint.gd` gives long-press previews on phones (`TouchHint.on_hover`). `ui/play/ui_settings.gd` stores the text size, the touch layout and the autopilot cooldowns in `user://settings.cfg`, not in the save. Touch targets are at least `touch_target_px` tall.

**Older prototype, not used by the game:** `core/battle`, `core/lineage`, `core/fate`, `core/economy`, `core/crafting`, `core/equipment`, `core/legacy`, `core/simulation`, `core/generation`, `world/`, `ui/screens`, `ui/components`, `ui/animations`, and the `tests/test_*.gd` files that don't start with `test_game_`. Nothing in the playable game refers to them. Don't extend them unless asked, and check before treating their tests as a gate.

## Conventions

- Old saves must keep loading. Missing keys fall back to defaults, and corrupt values must not crash loading, so check the type (for example `typeof(v) == TYPE_BOOL`) before using a saved value.
- A change that alters autopilot or auto-battle results is a balance change. Say so in the PR and show the before and after numbers.
- Commit the `.uid` file Godot generates beside each new script, so script references stay stable. Never commit anything under `.godot/`.
- Documentation: `docs/GDD.md` is the design, `docs/ROADMAP.md` lists what is done and what is next, and `docs/MOBILE.md` covers touch, text size and the Android and iOS export setup, `docs/BALANCE.md` covers the balance harness, `docs/ART.md` covers the battle sprites and their format, `docs/ART_STYLE.md` how new art should look, and `docs/RELEASING.md` covers publishing the APK and the Windows exe through GitHub. `TESTING.md` describes how the game's headless suites run. The `GutTest` files among the older prototype tests need an addon that isn't in this repo.
